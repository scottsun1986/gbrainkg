## 4. 优化点重点验证

### 4.1 RLS 租户隔离（C-04）

在演示环境以**仅持"普通用户"角色**的账号实测：

| 场景 | 期望 | 实际 |
|---|---|---|
| 访问管理员数据面 `/api/v1/admin/data` | 拒绝 | **403** |
| 查看他人知识库的文档列表 | 拒绝且不暴露存在性 | **404** |
| 检索他人知识库中的内容 | 拒绝 | **403** |

结论：**跨租户读取被有效阻断**，且不泄露资源存在性。`public` schema 下已**没有任何表缺少 FORCE RLS**（`_prisma_migrations` 除外）。

### 4.2 审计完整性

- 审计行正常写入（回归期间累计 11 行）。
- 审计写入失败：**0**。

期间修复了一个只在运行时暴露的缺陷：PostgreSQL 对 `INSERT ... RETURNING` 会用该表的 **SELECT 策略**校验返回行，而拒绝时报的是 WITH CHECK 措辞（极具误导性）。审计表读策略为"仅 service/管理员"，导致所有非管理员上下文的插入（含失败登录）被拒。已将审计写入改为 `createMany`（不带 RETURNING），**读限制保持不变**。

### 4.3 检索路径未被新策略打断

新增 RLS 后，检索路径（会读取 `ChunkSparseEmbedding` / `ChunkLexicalDoc` / `KbLexicalStat` / `LexicalTermStat`）按**文档/知识库可读性**收敛而非 service-only，实测 `/chat/search` 正常返回，未被策略阻断。

### 6.2 发布基础设施缺陷（2，本轮新发现，**优先级最高**）

**INF-01｜发布脚本顺序会把生产留在坏状态。**
`deploy-prod.sh` 的顺序是 `rsync → migrate → 校验 → 构建/重启`。校验失败时**迁移已落库但代码未重启** ⇒ "新 schema + 旧代码" ⇒ **登录 401**。本次发布中 **inst1 与 inst2 都真实进入过该状态**，均靠人工补构建+重启恢复。
建议：失败自动回滚，或将校验前置到迁移之前。

**INF-02｜新校验器规则过宽，必然失败。**
`verify-runtime-rls.sql` 要求"public 下任何启用 RLS 的表都必须 FORCE 且有策略"，而应用与 **gbrain 共库**，gbrain 自有的约 47 张表（`pages`、`content_chunks`、`minion_jobs`、`oauth_tokens` 等）本就"启用未 FORCE"，于是校验恒定失败 —— 它是把外部工具的私有表当成了本应用的发布门禁。
建议：把扫描收敛到应用自己的表集合，或显式豁免 gbrain 的表。

**由此产生的必须记录事项**：本次生产发布**跳过了发布门禁**（`--skip-gate`）。原因即 INF-02；且因绕开脚本重启步骤，脚本生成的发布快照与最终状态不完全对应。

## 7. 相对优化前的实质改进（已确认部分）

- **安全**：越权触发全租户重建、跨租户缓存串号、GBrain 推送关闭 TLS 校验、约 20 张租户表 RLS 缺失、通配权限批量提权（H-16）、非时序安全凭据比较、MFA 重放、CORS 白名单绕过、知识图谱与文档列表绕过 per-document ACL —— 全部收敛；`public` 下现已无表缺 FORCE RLS。
- **可靠性**：Outbox 认领 TOCTOU 与死信、文档版本发布竞态、连接器重同步破坏原始文件、压缩包与文本入库幂等、无界缓存 DoS（planCache / scopeDomainTermsCache）、流式取消传播与截止时间控制。
- **解析服务**：Office 网格上限、解压炸弹、上传内存物化、OCR 并发控制与 SSRF、子进程输出上限、事件循环阻塞治理。
- **发布与测试基础设施**：默认发布执行静态/单测/离线检查、门禁阈值单一真源、fail 与 skip 可区分、运行时 RLS 只读校验接入部署（即 INF-02 所指的那个）。

## 9. 修复记录（报告发布后追加）

§6.2 的两个发布基础设施缺陷已修复并同步到生产两个实例与演示环境。

### INF-01｜发布顺序

`scripts/deploy-prod.sh`：**迁移后的校验不再中止发布**。校验失败时只在发布目录写入标记并继续，确保服务被重启到与迁移后 schema 一致的代码；**重启之后**再按标记判定发布失败并非零退出。

即在"校验失败"与"服务跑在不一致的代码上"之间，选择了前者 —— 后者会 401 掉全部登录，前者只是发布未通过（可回滚）。

### INF-02｜校验器范围

`scripts/verify-runtime-rls.sql`：违规扫描的条件从"任何启用 RLS 的表都必须 FORCE 且有策略"收紧为**"有策略但未 FORCE"** —— 后者才是真正危险的形态（属主会绕过自己的策略）；而"启用 RLS 但完全没有策略"是 GBrain 对自己私有表（`pages`、`content_chunks`、`minion_jobs`、`oauth_tokens` 等约 47 张）的既有约定，不再被判为发布失败。

另对一张共享库中的外来遗留表 `AuthorizationRevision`（空表、仅一条 SELECT 策略、不属于本仓库 schema）做了显式豁免并注明理由，避免改动其它工具的安全姿态。

| 隔离库 `verify-runtime-rls.sh` 回归 | **PASS** |
