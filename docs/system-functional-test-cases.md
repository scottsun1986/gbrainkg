# LLMWiki 企业级知识库平台系统功能测试用例

> **版本**：v7.1 基线  
> **用途**：本地测试环境（Web `:3200`、API `:3202`）功能验收、回归测试与发布门禁。  
> **原则**：先在本机完成 P0/P1 及受影响回归，再由业务方确认后方可发布生产。本文以当前实现的接口和权限服务为准，而非仅以页面展示为准。

## 1. 测试范围、判定与术语

覆盖登录、会话、菜单、组织、人员、角色、三级知识库、文档入库/预览、行业库授权、问答、个人记忆、知识图谱、模型/OCR、GBrain 编译与 Dream、审计和运行监控。每个有权限边界的用例均应执行两次：

1. **UI 验证**：无权菜单、标签、操作按钮不可见或不可用；有权入口可正常使用。
2. **API 越权验证**：使用浏览器开发者工具或接口工具携带该用户令牌访问写接口，必须返回 `401`、`403` 或资源不可见时的 `404`，且数据库、文件和 GBrain source 均无变化。

本文的“发布知识”指知识被上传或录入后，经异步处理最终变为 `published` 并进入可检索 source；当前系统没有独立的人工“发布”按钮。可执行上传、录入文本、重试、删除的人员即为“知识维护者”。

| 优先级 | 含义 | 通过标准 |
| --- | --- | --- |
| P0 | 安全、数据隔离、核心可用性 | 全部通过；任一失败禁止发布 |
| P1 | 主业务闭环、可追溯性 | 全部通过；失败须修复或获书面豁免 |
| P2 | 易用性、兼容性、异常恢复 | 记录缺陷并在发布前评审 |
| P3 | 体验、性能优化、非阻断能力 | 纳入后续迭代 |

## 2. 权限规则基线（验收依据）

### 2.1 内置角色与能力

| 角色 | 权限入口 | 资源范围/限制 |
| --- | --- | --- |
| 普通用户 | 对话、可读知识库、知识图谱 | 只有 `chat.use`、`kb.read`；不能管理组织、人员、角色、行业库或模型 |
| 组织管理员 | 组织、人员后台入口 | 必须同时拥有“组织管理员”角色和至少一个有效管理根；管理根为本人组织成员节点或显式组织管理员节点，范围是该节点及全部下级 |
| 行业库管理员 | 行业库管理、行业库授权入口 | 角色只提供模块入口；对某一行业库能维护内容/授权，仍必须是该库的 KB 管理员；创建者和管理员的日常权力不同 |
| 行业库创建者 | 行业库管理入口、创建行业库 | 可创建行业库；自己创建的行业库可设置管理员、归档删除；当管理员交接给他人后，创建者不能上传、删除、重试文档或变更阅读授权 |
| 系统管理员/超级管理员 | 全部入口 | 全局组织、用户、角色、模型、审计、运行监控及非个人库管理；**不能查看、读取、删除其他人的个人库** |

`*`（系统级）角色仅可由系统管理员授予或操作。将“组织管理员”角色直接授给没有任何组织管理根的人，不应显示组织/人员管理能力；把某人设为组织节点管理员时，系统应自动补充“组织管理员”角色。

### 2.2 知识库类型、可读范围和维护范围

| 类型 | 谁能阅读/检索/预览 | 谁能上传、录入文本、重试、删除文档 | 谁能删除库/设置管理员/授权 |
| --- | --- | --- | --- |
| 个人库 | 仅 owner；系统管理员也不可见 | 仅 owner | 仅 owner 删除；禁止共享和设置管理员 |
| 组织库 | 节点本身及**下级节点**成员可见；上级成员不可反向看到下级库；系统管理员可读 | 该组织节点或祖先节点范围内的组织管理员，以及系统管理员 | 组织库随组织激活/停用；组织管理员可在自己范围内激活/停用并设置该组织管理员；不能作为普通 KB 归档删除 |
| 行业库 | owner、KB 管理员、以及通过人/角色/组织获得有效授权者；组织授权包含该组织的下级成员 | 当前 KB 管理员、系统管理员；**行业库创建者在不再是 KB 管理员时不可维护文档** | owner、KB 管理员、系统管理员可设置管理员、归档删除；仅 KB 管理员、系统管理员可新增/撤销阅读授权 |

### 2.3 组织和人员管理边界

| 操作人 | 可创建/编辑/归档组织 | 可设置组织管理员 | 可新增/编辑/禁用人员 | 不得执行 |
| --- | --- | --- | --- |
| 系统管理员 | 任意节点；可创建根节点、移动到根 | 任意有效组织 | 任意人员、任意角色 | 无本表内限制（个人库仍受私密规则限制） |
| 组织管理员（根=A） | 仅 A 与 A 的所有下级；只能在可管理节点下新建子节点 | A 与 A 的所有下级 | 仅组织归属至少有一个在 A 子树的人员；新人员所有归属必须在 A 子树 | 创建根节点；管理 A 的上级/兄弟节点；将人移到范围外；授予/操作系统级角色 |
| 普通用户、行业库角色 | 无 | 无 | 无 | 以上全部 |

**多归属用户边界**：当前实现中，目标用户只要存在一个组织归属落在操作者管理树内，组织管理员可对其执行编辑/禁用；但当编辑该用户的 `orgIds` 时，提交的所有组织都必须在操作者管理树内。本用例集必须验证这一点，作为显式安全决策。

## 3. 测试数据与账号矩阵

测试开始前用系统管理员建立以下隔离数据。账号密码使用一次性测试密码，禁止在文档、截图或 Git 中记录生产密钥。每个案例执行后按“清理”列恢复数据或使用独立前缀 `TST-YYYYMMDD-`。

### 3.1 组织树

```text
TST-集团
├── TST-研发中心 (RDC)
│   ├── TST-开发组 (DEV)
│   └── TST-测试组 (QA)
├── TST-合规部 (COM)
└── TST-市场部 (MKT)
```

创建并发布下列验证知识：`RDC-组织库` 含“研发管理办法第十四条”；`DEV-组织库` 含“开发组私有规范”；`COM-组织库` 含“合规管理办法”；`IND-A` 含“行业测试标准”；每人创建一个个人库。所有测试文档需使用唯一关键字，例如 `TST-RDC-14-20260905`，避免命中历史数据。

### 3.2 测试人员

| 标识 | 初始组织/角色 | 专门用途 |
| --- | --- | --- |
| SA | 系统管理员 | 全局操作、配置、对照组 |
| OA-RDC | RDC 成员 + 组织管理员 + RDC 组织管理员关系 | 本级及下级组织边界 |
| OA-DEV | DEV 成员 + 组织管理员 + DEV 组织管理员关系 | 下级不能反管上级 |
| OA-ROLEONLY | RDC 成员 + 组织管理员角色，无 OrgAdmin 关系 | 角色有、管理根无的菜单边界 |
| IC | 行业库创建者，`IND-A` owner，不是 KB 管理员 | 创建者保留库治理但失去内容维护 |
| IA | 行业库管理员角色 + `IND-A` KB 管理员 | 行业库日常维护、授权 |
| IA-NOROLE | `IND-A` KB 管理员、无行业库管理员角色 | 资源管理权与菜单入口分离 |
| READER-RDC | RDC 成员 + 普通用户 | 组织库只读、上/下级可见性 |
| READER-DEV | DEV 成员 + 普通用户 | 可见 RDC，不可见 DEV 以外的兄弟/下级库 |

| RG-ROLE | 普通用户 + `TST-行业阅读角色` | 角色动态授权 |
| RG-ORG | QA 成员 + 普通用户 | 组织动态授权 |
| MULTI | DEV + COM 双归属普通用户 | 多归属和组织管理员边界 |
| DISABLED | 已禁用用户 | 登录与既有令牌失效验证 |

### 3.3 行业库授权数据

对 `IND-A` 分别建立：READER-COM 的“人员授权”、`TST-行业阅读角色`的“角色授权”、QA 的“组织授权”、一条已过期授权。后续新增一个 QA 员工和一个具备该角色的员工，用于验证授权自动生效；撤销角色/移出组织后验证自动失效。

| ID | P | 前置/操作 | 期望结果 |

| AUTH-01 | P0 | SA 使用正确用户名密码登录 | 返回有效会话，进入工作台；`/auth/me` 显示当前用户而非密码散列 |
| AUTH-02 | P0 | 使用错误用户名、错误密码、空字段各登录一次 | 明确失败，不泄露“用户是否存在”、密码或堆栈 |

| NAV-04 | P2 | 切换亮/暗主题、刷新、重新登录 | 风格切换正确且不影响业务；偏好按产品设计持久化 |

## 16. 核心验收：知识可见范围、召回准确性与全链路完整性

本章是本系统的**发布核心门禁**。菜单、按钮和接口通过并不代表知识系统通过验收；必须同时证明：

1. 每个用户的候选知识集合恰好等于其权限集合，既不漏掉应见知识，也绝不混入越权知识；
2. 每个可回答问题都能从可见知识中召回足以支持结论的原文；
3. 回答中的结论、引用、预览链接、图谱节点、历史会话上下文和缓存使用同一个权限边界；
4. 入库、权限变更、删除、重建与 Dream 之后，以上结论仍成立。

### 16.1 权限真值集（Oracle）与对账方法

测试人员不得以“页面看见几个库”作为可见性结论。先在表格中人工计算每个测试账号应可见的知识库 ID，并与以下四个实际输出逐一比较：

- `GET /api/v1/session/bootstrap` 的 `kbs`；
- `GET /api/v1/kbs` 的列表和每个库的 `canWrite/canDelete`；
- 对话处理链路中“权限范围判定/GBrain source 选择”的 source、scope、候选证据；
- `GET /api/v1/knowledge-graph` 的文档节点，以及文档详情、文件、预览、compile-truth 接口。

期望集合计算式为：

```text
可见库 = 本人 active 个人库
       ∪ (本人所属组织节点及每个节点的所有祖先组织库)
       ∪ (对本人有效的行业库：直接人员授权 ∪ 当前角色授权 ∪ 本人组织及其祖先节点授权)
       ∪ (本人是 owner 或 KB 管理员的 active 非个人库)
       ∪ (系统管理员的所有 active 组织库和行业库)
```

其中“组织库可见”须特别按树方向核对：组织库授权给节点 **X** 时，X 及 X 的下级成员可读；上级成员不能因此读取 X 的库。个人库永远不进入任何他人的集合，系统管理员也不例外。

### 16.2 金标准知识集与问题集

建立独立的版本化验收知识集 `TST-RAG-GOLDEN`，不得使用生产真实敏感资料。每篇文档只放入指定库，并在正文、表格、图片 OCR 和标题中放置唯一事实。每题都登记：允许回答者、禁止回答者、标准答案、**必须出现的支持性原文片段**、允许引用的文档 ID、禁止引用的文档 ID。

| 类别 | 最少样本 | 必须覆盖的能力 |
| --- | ---: | --- |
| 精确条款 | 20 | “第十/十四条是什么”“共多少条”“条款例外条件”；同一制度跨章节、多页 |
| 同义/口语问法 | 20 | “上班时间/考勤时段”“怎么报名/报名流程”“研发考核等级” |
| 表格和列表 | 10 | Excel、DOCX/PDF 表格中的等级、阈值、日期、责任人 |
| 长文完整性 | 10 | 全文条款数、跨段条件、前后例外、附录；避免只取首 chunk |
| 多文档综合 | 10 | 两至三份**同一权限范围**文件的交叉结论；每项结论有来源 |
| 冲突和版本 | 10 | 新旧制度冲突、废止标记、同名不同版本；要求说明冲突而非盲目合并 |
| 扫描件/图片/PPT | 10 | OCR 文字、页码、图表说明、幻灯片标题与内容 |
| 无答案/无权限 | 20 | 当前可见范围没有答案、答案仅在无权库、问题完全无关 |
| 多轮指代 | 10 组 | 首轮明确实体，后续“它/上述/第十条”正确继承会话，而新会话不继承 |

每次发布至少执行 100 道题；涉及解析器、embedding、rerank、GBrain 或权限改动时执行全量题集。问题不得以文件名关键词替代正文事实，避免只测标题匹配。

### 16.6 可交付物与缺陷判定

- 授权撤销、删除、组织移动后仍可通过旧 source、旧会话、预览 token 或缓存读取内容；
- 处理链路缺失 ACL、source 新鲜度、最终权限过滤或错误节点，导致无法定位问题。
