# RAG 答案提示词调研与问题定位（2026-10-07）

## 现场证据

在测试环境通过当前用户的登录、会话与 trace API 读取了 2026-10-07 05:40 UTC 的会话（问题：“员工绩效由哪几部分构成。”），未绕过应用权限读取数据库。

该次答案说明“研发人员绩效考核指标体系由三类指标构成，但资料在此处中断，未列出具体名称”，另列绩效管理的五个环节。

trace 显示：召回 40 条、重排后 27 条，证据选择最终仅保留 2 条；未校准模式的 `effectiveFloor=0.2` 淘汰了同文件的后续列表块；`answer_context.contextChars=883`、`stitchedCount=0`。进入模型的指标规定确实止于“由三类指标构成：”。此前同用户同问的成功召回包含后续指标列表，但生成答案仍出现群体范围扩大与不必要的细指标展开。

因此有两个独立问题：列表续块在证据选择中丢失；答案提示规则未清楚区分组成、评价指标和管理流程，且强制展示全部相关框架会偏离问题。提示词无法恢复没有进入上下文的事实。

## 主流厂商建议及本项目采用方式

- [OpenAI Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering)：分开指令、示例和上下文，用输入/输出示例说明所需行为。采用带标签的静态决策顺序与虚构的正向示例；实际来源仍单独组装并使用原始编号。
- [Anthropic Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)：长文任务先定位来源中的相关原句，以减少无关内容干扰。采用先找直接支持所问关系的句子，再核对主体、名称、数量与范围的规则；用户只看到答案。
- [Google Prompt design strategies](https://ai.google.dev/gemini-api/docs/prompting-strategies)：指令要明确，术语与参数要解释清楚，示例格式保持一致。采用明确的问项分类与三组统一格式示例，保留中英双语行为一致。

以上是厂商提供的提示设计方法。本项目对“对象、关系、范围、粒度”作优先判定，以及对续列表证据的要求，是结合现场失败作出的工程设计，厂商文档不保证具体模型必然遵守。

## 提示词改动

1. 先判定准确主体、所问属性、范围及粒度；组成、评价指标、管理流程与结果用途不能相互替代。
2. 检查全部已提供来源，识别标题、冒号和数量引导句后的中断；有明确一致的完整条款时引用实际列举项的来源，局部片段不能推翻完整片段。
3. 有一个直接匹配问项时，主答后即结束。只有问题文本本身存在实质歧义且无法优先确定直接问项时，才呈现其他解释；资料中存在另一相关框架本身不构成问题歧义。
4. 首句保留来源中的子群体与条件，取消可能促使模型删掉限定的硬性字数约束。在回答选择阶段明确先由原文明示范围确定语法主语，再选组成项；范围要求优先于简短要求。正向示例使用“全部套装”的宽范围问题与“试点套装”的窄范围来源，答案首句直接使用窄范围。
5. 用虚构馆藏场景演示组成与流程区别、完整列表与部分引导句区别、以及仅限片段的缺失声明。示例明确标为非本次证据，不写入绩效业务规则。
6. 只问组成、数量或类别时，只给名称、所问数量、必需范围与角标；权重、占比、子指标及流程说明须由用户明确要求，且仍需直接证据。每个列举项与数值绑定实际支持它的来源，合并角标要求每个来源均支持该条具体断言。

## 验证边界

`answer-prompt.spec.ts` 维护双语规则及相互冲突规则的移除检查。这只证明提示词合约已组装，不能替代真实模型测试。真实回归应确认续块进入上下文后，模型给出有范围限定的指标类别，按问题粒度控制长度，并为实际类别引用包含该类别的证据。

第一轮修复后的实时回归已能限定为研发人员，并列出业绩、能力、行为三类；但仍主动加入未被用户要求的权重区间，并合并多个来源角标。可见 API 片段只明确展示其中一项权重，不能仅凭这些片段确认其余数值的引用支撑，因此该轮只证明类别与范围改善，不能证明数值完全接地或回答粒度合格。

第二轮补强第 6 项规则后，实时回归的核心答案、研发人员范围与组成类别正确，也没有主动附加权重；但仍追加用户未问的“五个管理环节与三类指标区别”。这暴露出“简单列举只输出所问字段”和“另一个解释合理就补充”的提示冲突。

第三轮将允许替代理解的条件统一收紧为“问题文本本身存在实质歧义，且无法优先确定一个直接匹配问项”。实时输出已简短，没有附加权重或管理流程，但又将原文“研发人员”泛化成“员工”。因此该轮改善了粒度，仍未满足主体范围要求。

第四轮将范围选择提升到组成项选择之前，并在示例首位加入宽范围问题对应窄范围答案的正向示例；实时验证已通过窄范围、只列名称与不附权重或流程的要求。

用户进一步明确所有提示词不得出现与具体问题相关的硬编码。第五轮仅将范围示例改为与本题领域无关的虚构“全部套装 / 试点套装、卡片 / 标签”，保留抽象规则，并加入最终中英文提示字符串不含本题领域词的检查。Luna 提示词测试 8/8 通过、API 构建通过；测试服务重启后的健康检查正常。泛化后 cy 实时答案为“软件研发中心研发人员绩效考核指标体系由业绩指标、能力指标、行为指标三类指标构成”，保留窄范围、没有权重或管理流程附注。负向检查针对应用维护的静态提示规则；完整请求仍会自然包含用户问题和检索到的源材料。

API 返回的精简 snippet 可能小于生成时完整上下文，数值支撑最终应以实际入模证据或完整来源检查为准，不能把 snippet 中未显示直接等同于原文没有。
