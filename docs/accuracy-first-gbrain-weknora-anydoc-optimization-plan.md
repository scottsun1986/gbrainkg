# 企业知识问答准确性优先升级方案

> 版本：2026-09-07（修订）  
> 范围：GBrain、AnyDoc、WeKnora、文档入库、混合检索、权限、Dream、安全渲染、可观测性  
> 发布原则：所有开发必须先在本机测试环境验证，通过验收并经业务方明确确认后，才能发布生产环境。  
> 关联文档：[源码复核与优化方案](source-review-weknora-anydoc-2026-09-06.md)、[实施台账](optimization-implementation-status.md)

## 1. 目标与结论

本方案的第一目标是回答准确、可验证、零越权，而不是单纯追求首字节速度或增加模型数量。

推荐采用“单一回答证据主源、能力分层”的架构：

```text
AnyDoc / 百度 OCR
        ↓
高保真文档标准化
        ↓
条款、章节、父子块、表格、页面索引
        ↓
GBrain Source + Compiled Truth + Timeline
        ↓
权限 Scope / Scope Fingerprint
        ↓
BM25 + 向量 + 标题条款 + 图谱信号
        ↓
RRF 融合 + Rerank + 文档通读
        ↓
证据门禁 + 版本校验
        ↓
带来源链接的最终回答
```

核心判断：

1. AnyDoc 适合作为办公文档和文本型 PDF 的统一解析器。
2. 扫描版 PDF 必须经过 OCR 和版面恢复，不能把 OCR 失败的文本直接入库。
3. GBrain 负责知识编译、Compiled Truth、Timeline 和权限范围内的知识演进。
4. WeKnora 不作为第二套最终回答数据库，而作为可选外部检索器或完整文档读取器。
5. 图谱只作为召回扩展和关系信号；没有可验证的文档版本、Chunk 和来源时，不得直接作为回答证据。
6. 所有答案必须经过权限、版本、证据覆盖率和冲突检查。

GBrain 官方模型强调 Compiled Truth、Timeline、语义分块和递归分块结合；WeKnora 官方能力包含混合检索、文档通读和来源标识；AnyDoc 官方说明本地处理文本型 PDF，但扫描 PDF 需要额外 OCR。实现时吸收这些机制，但不照搬另一套系统的权限和数据模型。

## 2. 当前本地实现评估

### 2.1 已有能力

- API Node 已接入 `@firecrawl/anydoc` 固定版本 0.2.4，支持 `toMarkdown`，生产路径统一由 API 持有。
- AnyDoc 转换失败后（含 `needsOcr`、`encrypted`、`resourceLimit`）进入 Parser Worker 回退链路。
- Parser Worker 已区分解析引擎、PDF 四分类（native_text/scanned/mixed/empty）、百度 OCR 页级处理和并发容量。
- 所有转换结果统一执行 `content-v1` 质量门禁（`content-quality.ts`），解析成功不等于内容可发布。
- API 使用单例 Prisma 客户端，降低多连接池造成的 PostgreSQL 连接耗尽风险。
- GBrain Adapter 已具备子进程并发限制（`ProcessSemaphore`）、超时、8 MiB 输出限制、取消和 Source 状态缓存。
- ChatService 已实现 21 阶段流式管线，包含多 Source 查询（`queryMany`）、上下文预算、历史对话消歧、权限双层校验、证据分数门禁、检索升级和取消传递。
- GraphRAG 模块已接入知识图谱页面和社区构建，但已在聊天管线中显式跳过（`trace.skip`），因为缺乏可验证来源绑定。
- Provider、LLM、Embedding、Rerank 配置已进入平台数据库，支持 5 秒热缓存和签名化路由，可在界面管理。
- Web 已使用 DOMPurify 净化 Markdown 渲染，CSP 已移除 `unsafe-eval`。
- BrainChangeEvent Outbox 机制已建立，用户/组织/授权高风险写路径已改为与事件同事务。
- 跨 Source 合并已按 Source + KB + 文档/slug 去重，不同来源同名页不再互相覆盖。
- 候选镜像（API/Web/Parser）已构建；GBrain 启动断言 `0.47.6.0`。

### 2.2 当前缺口

- **评测集空白**：无标注评测数据集，无自动化 RAG 质量指标（Recall@K、MRR、引用正确率），优化无客观依据。
- **条款级切分缺失**：分块无条款识别逻辑，"第十条"类精确查询回答受限。
- **图谱表迁移不一致**：`GraphEntity`/`GraphRelation`/`GraphCommunity` 在 Schema 中但缺配套 SQL migration，新环境部署图谱静默失效。
- **Outbox 事务覆盖不完整**：部分写路径已改为同事务，但用户创建等路径仍待迁移，补投和 dispatcher 幂等尚未完整验收。
- **AnyDoc 解析入口仍有两处**：API npm 和 Parser CLI 并存，存在重复解析和容器能力不一致风险。
- **中文 token 估算不准**：`length / 4` 为粗略英文估计，中文场景偏差较大，影响上下文预算。
- **GBrain Adapter 非单例**：多个 Service 各自 new Adapter，各持独立并发池，`GBRAIN_MAX_CONCURRENCY` 不是进程合计。
- WeKnora 目前只有只读适配器和契约测试，尚未接入实际问答检索链路。
- 当前 GraphRAG 正则启发式抽取缺乏 NER，关系未绑定可验证的文档版本和 Chunk，已在聊天管线中跳过。
- 文档结构仍需进一步提升到条款和页面级别。
- 第三次权限校验（引用输出时独立 ACL 复核）的独立性尚待验证。

## 3. 高保真入库流程

### 3.1 原始资产与版本

每次上传都必须保留（已实现的标记 ✅，待补充的标记 ☐）：

- ✅ 原始文件对象和原始文件名（`rawFileOid`、`title`）；
- ☐ 文件内容哈希（用于去重和变更检测）；
- ✅ 文档版本号（`version`）；
- ✅ 上传人、知识库、组织（`kbId`、用户身份）；
- ✅ 解析器及版本（`parserEngine`、`parserClassification`）；
- ☐ OCR 服务、模型和请求批次（Parser Worker 内部处理，API 侧未持久化完整 OCR 元数据）；
- ☐ 解析时间、耗时和错误码（部分记录于日志，未结构化存储）；
- ✅ 原始文件与标准化内容的关联关系（`rawFileOid` → `mdPath`）。

禁止用新的 Markdown 直接覆盖原始文件，也禁止把低质量解析结果伪装成 `published`。

### 3.2 按文件类型路由

| 文件类型 | 首选处理 | 失败/补充处理 | 发布条件 |
| --- | --- | --- | --- |
| TXT/MD/HTML/CSV | 原文快速通道或结构化解析 | 编码检测、HTML 清洗、表格规范化 | 文本非空且无严重乱码 |
| DOC/DOCX | AnyDoc | Legacy DOC 使用专用转换器回退 | 段落、表格顺序可恢复 |
| PPTX | AnyDoc | 幻灯片结构、备注、图片 OCR 补充 | 页/幻灯片边界和标题保留 |
| XLS/XLSX | AnyDoc | 工作表、表头、行列关系恢复 | 工作表和表格语义可检索 |
| 文本型 PDF | AnyDoc / PDF 结构解析 | 页码和版面校验 | 页面文本完整、质量通过 |
| 扫描版 PDF | PDF 分类后百度 OCR | 版面恢复、表格 OCR、页级重试 | OCR 质量达到阈值 |
| 图片 | OCR 和图像元数据 | 人工复核 | OCR 文本质量达到阈值 |

### 3.3 PDF 分类

PDF 必须先计算每页的文本密度、字符数量、图片覆盖率和字体提取质量：

- 可读版 PDF：优先使用原生文本和版面结构；
- 扫描版 PDF：进入百度 OCR；
- 混合 PDF：按页分别路由，不能把整份文档粗暴地归为一种类型；
- OCR 失败页：保留页号和失败原因，进入待复核，不得静默跳过。

### 3.4 质量门禁

质量检查至少包括（已实现 ✅ / P1 增强 ☐）：

- ✅ 中文字符和数字占比（`meaningful_characters`）；
- ✅ `U+FFFD` 替换字符比例（阈值 > 1%）；
- ✅ 控制字符比例（阈值 > 2%）；
- ✅ OCR 页的置信度（阈值 < 0.75 警告）；
- ✅ 图片占位符检测（PPTX/图片类型）；
- ✅ 引擎拒绝/审核结论不可被覆盖；
- ☐ 页面/幻灯片覆盖率（P1）；
- ☐ 空段落和重复标题比例（P1）；
- ☐ 表格行列完整性（P2）；
- ☐ 条款编号连续性（P2）；
- ☐ 文档标题和正文一致性（P2）。

状态建议：

```text
parsing → parsed → quality_review → indexing → published
                         ↓
                      failed/rejected
```

质量状态和解析状态必须分开。解析成功不等于内容可发布。

## 4. 结构化切分与索引

### 4.1 多粒度块

同一份文档按阶段建立不同粒度的块：

**P0（条款级切分，解决精确查询缺口）：**

1. 条款块，例如"第十条"，保存 `article_no`、`chapter_no`、`page_no`、`parent_chunk_id` 和原文位置；
2. 页面或幻灯片块，保存 `page_no`。

**P1（结构增强）：**

3. 章节父块；
4. 表格行/表头块；
5. 父子块检索：子块负责命中，父块负责补充上下文。

**P2（深度索引）：**

6. 文档级摘要块（由 GBrain Compiled Truth 承担）；
7. 时间线和版本变化块。

当前 `markdown-chunker.ts` 仅按标题和 token 边界分块，P0 需要增加条款识别正则和页码索引。

### 4.2 两种分块策略

- 递归分块：用于 Timeline、批量导入和格式稳定的基础索引；
- 语义分块：用于 Compiled Truth 和高质量正文，按主题边界切分；
- 条款分块：对制度、办法、规范、法律等强结构文档优先；
- 父子块检索：子块负责命中，父块负责补充上下文。

切分不能只使用固定字符数，否则“第十条”可能和前后条款断开，回答会缺少限定条件。

## 5. 查询与回答流程

### 5.1 查询规划

先判断问题类型，再决定检索策略：

- 精确事实：优先标题、实体、关键词和条款索引；
- 条款查询：识别文档名、条款号、章节号并执行定位；
- 清单/统计：读取文档目录和完整候选集合；
- 跨文档综合：启用广覆盖 Scope 和跨 Source 汇总；
- 对比问题：分别召回各文档版本，再执行对齐；
- 多轮指代：使用当前会话历史消歧，但以当前授权知识为准；
- 个人记忆问题：单独访问用户私有 Memory Source，不混入共享制度证据。

查询改写只能用于扩大候选集合，不能替换用户原问题，也不能直接作为答案依据。

### 5.2 四路并行检索

1. BM25/关键词检索；
2. Embedding 向量检索；
3. 标题、文件名、条款号和元数据检索；
4. 有来源绑定的图谱实体和关系扩展。

候选结果执行：

```text
RRF 融合 → 去重 → 父子块合并 → Rerank → 文档通读补充 → 最终 ACL 校验
```

### 5.3 证据不足自动扩检

以下情况必须扩检：

- 首条证据只有摘要或标题；
- 回答需要多个条款但只命中一个；
- 证据和问题实体不一致；
- 命中文档存在多个版本；
- 回答结论没有足够引用覆盖；
- 召回分数低于领域阈值；
- 文档内容疑似截断。

扩检顺序：

1. 扩大候选数量；
2. 读取命中条款的父级章节；
3. 读取相邻条款；
4. 按顺序读取命中文档的更多正文；
5. 检查版本和冲突；
6. 重新排序并进行证据门禁。

仍然没有证据时，必须明确说明未找到，禁止通用模型凭常识补答。

### 5.4 最终回答门禁

回答前校验：

- 每条证据属于当前用户授权范围；
- 文档和 Chunk 版本仍是最新有效版本；
- 结论与引用文本有语义支持；
- 引用覆盖主要结论，而不是只引用无关摘要；
- 存在冲突时列出冲突版本和生效时间；
- 需要完整条款时不得只返回部分切片；
- 每个来源提供可点击的在线预览链接。

## 6. 权限与 GBrain Source 设计

### 6.1 Source 原则

- 共享知识库使用共享 GBrain Source；
- 私密知识按权限组拆分 Source；
- 用户 Source 只做增量同步；
- Source 不承载最终权限判断，数据库 ACL 是最终裁决；
- 任何派生摘要必须记录来源 Source、文档版本和权限指纹。

### 6.2 Scope

Scope 由以下内容计算指纹：

- 用户身份；
- 用户组织和角色；
- 个人授权；
- 组织授权；
- 行业库授权；
- 可见知识库；
- 可用文档版本；
- Scope 规则版本。

权限变化时必须使相关 Scope 失效并增量重编译，不能继续使用旧的跨库摘要。

### 6.3 权限安全底线

检索前过滤一次，证据进入 LLM 前再过滤一次，回答完成后引用输出再过滤一次。任何一步发现越权都应终止该证据链。

个人知识库和个人记忆对其他用户不可见，包括超级管理员；超级管理员只能看到审计元数据，不应看到个人内容。

## 7. Dream、Compiled Truth 与图谱

### 7.1 事件驱动增量编译

以下事件触发受影响范围的增量编译：

- 文档新增、删除、更新；
- 解析质量状态变化；
- 知识库授权变化；
- 组织和角色变化；
- 行业库管理员或授权变化；
- 用户确认个人记忆；
- 文档版本生效或失效。

每次编译应生成可审计的运行记录：输入 Source、输入版本、影响 Scope、生成页面数、失败数、耗时和输出哈希。

### 7.2 Compiled Truth 使用规则

Compiled Truth 可用于：

- 广覆盖问题的初始候选；
- 跨文档主题综述；
- 查询规划和实体扩展；
- 高概率问题的低延迟预热。

但它不能替代原文证据。最终回答必须回到当前授权的原始 Chunk 和文档版本。

### 7.3 图谱规则

**当前状态**：图谱使用正则启发式抽取（标题、书名号、词尾匹配），社区使用 BFS 模板生成。ChatService 已显式跳过图谱上下文注入（`trace.skip`），因为缺乏可验证来源绑定。图谱仅用于发现页可视化。

**P2 目标**：图谱边必须保存来源文档 ID、文档版本、Chunk ID、页码或幻灯片号、关系抽取模型和时间、原文片段。在此之前，图谱不得恢复为回答证据。

**迁移方向**：优先复用 GBrain 官方 graph/links/facts 或 WeKnora 模型级抽取，而不是在正则基础上叠加版本绑定。若继续保留本地图谱用于发现页展示，已删除/撤回的文档对应的图谱条目必须被过滤或清理。

没有上述来源绑定的图谱只用于导航和发现，不参与答案生成。

## 8. WeKnora 的定位

不建议将 WeKnora 和 GBrain 同时作为最终问答主引擎，否则会出现重复索引、双重权限、两套答案生成和延迟增加。

推荐接入方式：

1. WeKnora 作为可选外部检索器；
2. 只发送当前 ACL 解析出的知识库和文档绑定；
3. 返回结果统一转换为本项目 Evidence；
4. 重新校验文档、版本、Chunk 和权限；
5. 优先使用 WeKnora 的混合检索和文档通读能力；
6. 不直接使用 WeKnora 生成的最终答案。

WeKnora 只有在满足以下条件时才进入生产查询：

- 外部服务可用性和延迟达标；
- 结果带稳定来源 ID；
- 能够绑定本项目文档和版本；
- 通过越权、版本和故障降级测试；
- 离线评测证明准确率有增益。

否则保留为灰度或离线对比通道。

## 9. 评测体系

建立至少 300 条企业真实问题组成的离线评测集，覆盖：

- 条款精确查询；
- 文档清单和数量统计；
- 跨文档综合；
- 多轮指代；
- 个人记忆；
- 组织库上下级可见性；
- 行业库个人/组织/角色授权；
- 文档删除和版本切换；
- 文本 PDF、扫描 PDF、PPT、图片、表格；
- 乱码、空文档和 OCR 失败。

核心指标：

| 指标 | 目标 |
| --- | --- |
| Recall@10 | 领域评测集持续提升 |
| MRR/NDCG | 关键证据尽量靠前 |
| 首条有效证据命中率 | ≥ 95% |
| 引用准确率 | ≥ 98% |
| 引用覆盖率 | ≥ 95% |
| 越权召回率 | 0 |
| 文档更新生效延迟 | 可观测并满足业务 SLA |
| P95 响应时间 | 在质量门禁通过前提下优化 |

所有检索、分块、模型、权限和 Dream 改造必须通过离线回放；不能以单个问题调规则。

## 10. 可观测性与故障定位

每次问答显示完整处理链：

```text
身份认证
  → 权限快照
  → Scope 解析
  → 查询规划
  → 个人记忆判断
  → Compiled Truth 检查
  → BM25
  → 向量检索
  → 标题/条款检索
  → 图谱扩展
  → RRF
  → Rerank
  → 文档通读
  → 最终权限校验
  → 上下文预算
  → LLM
  → 引用校验
```

每个节点记录：状态、耗时、输入摘要、输出数量、错误码、重试次数、Source/Scope 指纹和降级原因。密钥、原始个人内容和未授权文档内容不得写入日志。

## 11. 分阶段开发计划

### P0：准确性和安全底座

**评测与度量（第一优先）：**

## 12. 验收门禁

每次发布必须满足：

1. 本机完整构建通过；
2. API、Web、Parser 单元测试通过；
3. 浏览器 E2E 通过并保存截图；
4. 评测集无越权召回；
5. 条款、清单、跨文档和扫描 PDF 场景通过；
6. 问答调用链每个节点有状态和耗时；
7. 数据库连接、队列、解析器和 GBrain Source 健康；
8. 安全渲染回归通过（DOMPurify 净化、CSP 无 `unsafe-eval`、Markdown XSS 断言）；
9. 空库 Prisma migration 全链成功，无遗留 Schema 漂移；
10. 仅在业务方明确确认后发布生产；
11. 生产发布后执行同一套冒烟和回滚检查。

## 13. 当前建议

当前不应优先做"接入第二套完整问答引擎"，而应优先完成修订后的 P0：

1. **建立评测集**——没有评测集，所有优化都是盲目的，这是第一优先；
2. **条款级切分和页码索引**——解决"第十条规定了什么"类精确查询的核心缺口；
3. **补全图谱表 Prisma migration**（F03）——消除新环境部署的静默失效；
4. **Outbox 事务覆盖完整**（F07）——确保业务修改与事件一致性；
5. **AnyDoc 解析入口收敛**（F05）——消除重复解析和容器能力不一致；
6. **验证第三次权限校验独立性**——确保引用输出时的 ACL 不依赖缓存。

以下 P0 旧项已确认完成，不再列为待办：入库质量门禁（`content-v1`）、安全渲染（DOMPurify + CSP）、WeKnora 标记未启用、standalone Web 启动配置。

只有当 P0/P1 的评测结果稳定后，才决定是否启用 WeKnora 灰度检索。这样更有机会在本项目的政府、企业制度和多组织权限场景中获得真实的准确性优势。
