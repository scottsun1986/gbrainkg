## 3. 缺陷清单

### BUG-1(P1 → 已修复):创建用户接口 500(BrainRepo RLS 违规)
- **现象**(shot-10):管理界面"新增人员"提交后 toast "Internal server error",弹窗滞留,列表不刷新;但用户实际已落库。
- **根因**(API 日志):`AdminController.createUser` 内 `prisma.brainRepo.upsert()` 报 `new row violates row-level security policy for table "BrainRepo"`(Postgres 42501)。RLS_ENFORCE=1 下请求以 llmwiki_app(NO-BYPASSRLS)执行,插入 owner=新用户 的行与请求用户上下文(admin)不匹配。
- **次生影响**:用户/组织/角色已写入但 BrainRepo 行缺失;前端错误反馈误导 + 列表不自动刷新。
- **复测**:热修重建后(18:49 构建),带 orgIds 创建 → **HTTP 201**;不带组织 → 400 "At least one organization is required."。**已修复** ✅(UI 全流程建议在下一轮回归中复测)

### BUG-2(P1,未修复):组织管理员人员目录收敛异常(违背"本级+下级"设计)
- **设计基线**(用户澄清):组织管理员是节点级的,子组织管理员只能管理**自己这级和下级**的用户。
- **复现**:u_org10061830(组织管理员角色,OrgAdmin 挂在 E2E根组织-10061830 与 E2E受管部门-10061830;该子树下实有 5 名成员)登录 → 管理后台/人员管理 → "匹配到 1 / 1 人"(仅自己)。
- **API 证据**:GET /admin/data → `users=[u_org]`、`orgs=[E2E根组织-10061830]`;而同一响应的 `managedOrgIds` 正确包含 2 个节点、`capabilities` 含 org.read/org.user.read/org.user.manage/org.node.create。
- **矛盾点**:响应既不符合设计(应 5 人),也与源码 `directoryUsers` 分支(`canReadOrg → 全量 users`)不符 —— 强烈指向 **User/OrgAdmin/OrgNode 表的 RLS 策略在组织管理员请求上下文未按管理范围放行**(withServiceContext 覆盖或 GUC 设置不完整)。
- **影响**(shot-34):组织管理员无法查看/新增/停用本级及下级人员,人员管理职责实质不可用。

### BUG-3(P0,未修复):子组织管理员访问 /admin/data 整体 500
- **复现**(干净场景):创建 组织C(管理员=u_cadmin)→ 组织D 挂 C 下 → 成员 1 人挂 D;以 u_cadmin 登录 → GET /api/v1/admin/data → **500**。
- **根因**(API 日志):`orgNode.findMany()` include `admins.user` 时,RLS 上下文下他人的 User 行不可见 → Prisma "Inconsistent query result: Field user is required to return data, got `null` instead"。
- **UI 表现**(shot-35):管理后台可打开但组织拓扑树"共 0 个节点/暂无组织节点"(应显示 C/D 两级),500 被前端吞掉,无任何错误提示。
- **触发面**:任意存在"非本人可见的 OrgAdmin 关系"时,子组织管理员访问管理后台必现 —— 即组织管理员功能在多管理员共存场景下整体不可用。
- **关联**:与 BUG-2 同根因簇(User 表 RLS 可见性 vs 管理面 join 查询);修复时应一并处理"管理面清单查询需按管理范围显式放行"与"join 不可见行导致 Prisma 异常"两个问题。
- **附注**:API 日志另有 `Unknown argument compileStartedAt`(BrainScopeService 清扫任务)的 schema 漂移告警 —— 代码引用了数据库不存在的列,建议核对迁移一致性。

## 附:PostgreSQL RLS 在本项目的适用性评估(基于本次测试与修复的实证)

**结论:适合作为纵深防御层,不适合作为主权限引擎。本项目当前"应用层为主 + RLS 兜底"的混合架构方向正确,但需要把两类路径的边界制度化。**

### 本项目场景特征
- 单库多租户(多实例按库隔离,库内再按组织隔离)+ 三级知识库(个人/组织/行业)+ 文档级 ACL + 跨组织授权;
- 权限语义复杂且动态(管辖子树、行业库授权关系、KbAdmin、能力码),并非简单的"行属于租户";
- 应用层已有完整权限引擎(PermissionService:capabilities / managedOrgIds / visibleKbs);
- 数据敏感(企业知识资产),有审计与合规诉求(越权拦截留痕)。

### RLS 在本项目证明过的价值(本次实证)
1. **纵深防御真实有效**:首轮 BUG-2 中,应用层曾把目录语义写成"持 org.read 即全量",RLS 把结果硬收敛到本人——方向是"宁可拒绝不可泄露"。若应用层出现越权 bug,RLS 是最后一道闸。
2. **减少应用缓存陈旧风险**:权限变更经 invalidatePermissionCaches 主动失效;非 service 查询还受 DB 策略校验。DB 的事务快照/事务内可见性缓存仍影响变更可见性,不能承诺所有路径即时撤权;service 清单依赖应用范围校验。
3. **可审查的纵深防御**:策略集中在 DB,运行角色 NOBYPASSRLS。事务 GUC 区分用户与 service;应用可以显式设置 service,因此仍需审查提权点,不能据此声称每条查询均携带终端用户身份。
4. **实例库内隔离**:RLS 为同一实例库内的组织/用户资源提供兜底。10+ 实例共享中间件由专属数据库、Redis DB 及共享基础设施实现,不依赖 RLS。

### RLS 在本项目暴露的代价(全部为本次真实踩坑)
1. **策略与关系查询契约冲突(BUG-3 根因)**:Prisma 的 required to-one include(OrgNode.admins.user、KbAdmin.user、CompileJob.user)遇到不可见关联行时可能抛 "Inconsistent query result" 500。这是当前可见性策略与查询契约不匹配;应先采用可见关系投影/分开查询,仅确实需要跨用户授权清单时使用经过范围校验的只读提权,不能把所有跨用户 join 一律提权。
2. **授权计算悖论(BUG-2 第二层根因)**:computeManagedOrgIds 需要全量组织图才能算"管辖子树",但该查询以请求用户身份执行时只能看到自己的挂载链——"用 A 的身份算 A 能否管 B,却看不见 B 的存在"。授权计算被迫提权,与第 1 条叠加后,service 提升点越来越多,审计边界随之模糊。
3. **可观测性与调试成本高**:42501/null-in-required-field 这类错误不指向权限语义本身;本次两个缺陷各埋了两层根因,定位耗时远超应用层等价问题。策略在 DB 里,代码 review 与权限语义天然分离。
4. **性能开销**:策略函数/子查询会增加工作量。DB app_visible_kb_ids 缓存为事务内 GUC,与 PermissionService 默认 5 秒的进程内 TTL 缓存不同;不应把后者窗口归因于 DB 策略。
5. **双权限体系漂移**:应用层(PermissionService)与 DB 层(pg_policies)两套语义必须同步演进。BUG-2 本质就是两边对"组织管理员"语义理解不一致;本次修复后仍需人工约定"谁是权威"。
6. **运维与心智负担**:迁移顺序、角色权限(BYPASSRLS/NOBYPASSRLS)、GUC 事务作用域(forUser/forService/runAsAuth/withSystemWrite/withAdminInventory 五种上下文)——新人极易踩坑,且出错的形态是 500/静默过滤而非清晰报错。

### 建议(按性价比排序)
1. **明确双层分工并写入开发守则**:应用层(PermissionService)定义权限语义;RLS 保留独立兜底。用户查询默认保持用户上下文;授权内部关系读取走 withPermissionRead,已鉴权的管理清单走 withAdminInventory,系统产物写入走 withSystemWrite。提权不能由 join 自动触发,查询范围必须先于分页/截断,嵌套关系同样需要范围约束。边界与清单见 [RLS 开发边界](RLS-BOUNDARIES.md)。
2. **控制 RLS 策略复杂度**:新表按数据归属选择 owner/资源可见性/系统产物策略,不要默认系统管理员可读他人个人数据。复杂可见性复用已审查函数,SECURITY DEFINER 须固定 search_path、限制 EXECUTE 权限并验证返回范围。
3. **保留现有策略面**:User/OrgNode/OrgAdmin 仍服务认证、用户查询和权限计算;管理清单提权不代表这些表只用于管理面。实例已按库隔离,只保留实例级策略会丢失实例库内防泄露能力。本轮不放宽任何策略。
4. **可观测性补强**:为显式 RLS 拒绝、通用 42501 权限拒绝、required relation 缺失分别记录稳定事件。42501 不只表示 RLS,关系缺失也可能是坏数据。普通 SELECT 被 RLS 过滤不会报错,应靠权限矩阵/范围回归检测,不能承诺错误日志发现所有静默过滤。本轮提供可供日志平台告警匹配的事件,未连接外部告警服务。
5. 若项目重启架构,可评估"应用层集中鉴权 + DB 仅租户级防呆"的简化路线;但对现有系统,不建议移除 RLS——纵深防御与合规价值大于维护成本。
