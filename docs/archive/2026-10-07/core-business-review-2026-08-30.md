# GBrain 企业知识平台核心业务评估与优化验收

评估日期：2026-08-30  
评估范围：核心业务、文档入库、GBrain 检索、会话记忆、知识权限、在线预览、模型配置、生产运行

## 一、结论

本轮已完成代码级审查、生产数据核验、针对性改造和真实浏览器验收。系统当前已经形成可闭环运行的企业知识流程：

> 原始文件持久化 → 异步解析 → 规范 Markdown 与结构化分块 → 按有效读者集合写入 GBrain source → 增量同步与混合检索 → 数据库最终权限校验 → 大模型生成 → 原文引用与在线预览

架构遵循 GBrain 的核心理念，但没有机械复制官方 Company Brain 示例。官方示例主要表达“Git 仓库是知识事实源、source 是检索隔离边界、按组织共享 source”；本项目在此基础上增加了动态组织、角色和人员授权，以及数据库最终鉴权，更符合政府和企业多层组织场景。

当前版本适合在受控局域网内作为单节点生产系统使用。若面向互联网或大规模高并发，还应补充 TLS 网关、统一身份认证、多副本、集中监控和异机备份。

## 二、核心业务流程

### 1. 知识库治理

| 知识库类型 | 阅读范围 | 内容维护 | 库级治理 |
| --- | --- | --- | --- |
| 个人库 | 仅所有者 | 所有者可上传、增加文本、预览、删除知识 | 所有者可删除库，不支持共享 |
| 组织库 | 本组织及下级组织成员可读上级组织库 | 本级组织管理员及上级组织管理员 | 组织管理员管理本级及下级组织，不可管理上级或旁支 |
| 行业库 | 按人、组织、角色动态授权，组织授权包含下级 | 当前指定管理员 | 创建者始终可设置管理员、删除库；当前管理员可维护、授权和删除 |

“角色能力”和“资源范围”分开计算：角色决定是否出现管理入口，具体组织或行业库关系决定能管理哪些资源。所有写操作仍由 API 再次鉴权，前端隐藏菜单不是安全边界。

### 2. 文档入库

当前流程：

1. 接口校验登录身份、知识库可见性和维护权限。
2. 中文文件名正规化后保存原文件；文件名、扩展名和大小均受限制。
3. 数据库创建 `parsing` 文档记录，BullMQ 持久化任务，接口立即返回。
4. 解析服务按格式处理；DOCX 保留段落和表格顺序，复杂 PDF 优先使用 Docling，必要时降级。
5. 解析结果保存为规范 `content.md`，同时按标题语义切分并原子写入 Chunk。
6. 状态进入 `indexing`，根据知识库的实际读者集合定位共享或权限组 GBrain source。
7. source 仓库写入 `docs/<documentId>.md`，Git 提交后执行 GBrain 增量同步。
8. 同步成功才切换为 `published`；只有最终重试失败才标记 `failed`。

已增加的可靠性措施：

- 入库与编译任务持久化、指数退避和有限重试；
- 解析并发默认为 2，避免一个复杂 PDF 阻塞全部小文件；
- 服务重启后自动恢复陈旧任务；如果解析结果和分块已经存在，从编译边界恢复，不重复解析大文件；
- 删除文档时同时删除 GBrain source 文件、索引映射、数据库数据和原文件；
- 上传者返回姓名和用户名，不再只显示 ID；
- 中文 DOCX 文件名、解析状态和检索结果完成真实闭环验证。

### 3. GBrain source 组织方式

当前不是“每人一个完整 GBrain 副本”，而是：

- 对所有用户可见的知识使用共享 source；
- 其他知识库按“最终有效读者集合”分组，相同读者集合复用同一权限 source；
- 用户只维护自己可访问 source 的成员关系；
- 文档上传、删除和 ACL 变化均增量同步，不再完整重建每个用户仓库；
- 每 15 分钟执行权限成员对账，每日执行 GBrain `dream` 维护；
- source 是第一层检索隔离，数据库 ACL 是返回答案前的最终强制校验。

Dream 不是一个无条件生成“文档总结 Wiki”的任务。GBrain 的默认 `synthesize` 主要面向会话/纪要到反思页，`synthesize_concepts` 还依赖相应 lens pack；本项目的上传文档不会被自动改写成未经溯源的总结页。对非 default 的权限组 source，官方 Dream 还会跳过跨 source 的全局总结 phase，这是权限隔离的正常结果，不是同步失败。

Dream 的运行结果已持久化到 `BrainMaintenanceRun`。系统管理员进入“管理后台 → 审计日志”即可看到运行健康状态、最近运行、每个 source 的新增/变更/移除数量、GBrain phase 的 `ok/warn/skipped` 明细、队列失败和错误原因；队列失败最多指数退避重试 3 次，也支持“立即执行维护”复核。

这比每人复制一套索引节约存储和同步成本，也比只依赖 Markdown frontmatter 更安全。权限变化时即使 source 对账尚未完成，数据库最终校验仍会阻止越权证据进入模型上下文。

### 4. 查询与会话流程

1. 读取当前会话最近 24 条消息并按时间恢复。
2. 使用大模型把当前问题与历史语境改写成独立检索问题，同时识别“全文、全部、多少条”等宽检索意图。
3. 历史消息只用于消解“它、刚才、这份”等指代，不直接当作事实证据。
4. 根据用户当前可见知识库和页面选择范围计算 source。
5. 使用 GBrain 的查询扩展、向量检索、BM25、融合、图关系和重排能力检索；精确问题启用自适应截断，全文问题扩大候选并关闭过早截断。
6. 对每个候选的知识库和文档执行数据库最终 ACL 校验。
7. DeepSeek 只基于通过校验的证据和受限会话历史生成回答。
8. SSE 持续输出答案、引用和会话 ID；引用携带知识库、文档 ID、中文标题和原文片段，可直接打开在线预览。

总结 Wiki 与 RAG 的关系：当前 RAG 使用的是通过权限 source 检索到的规范原文页，再由数据库做最终 ACL 校验后送入 DeepSeek；Dream 产生的跨 source 总结页当前不会被默认当作证据。若将来启用总结页，应把它作为带 `derived_from` 原文文档 ID、生成时间和版本的“派生文档”写回同一授权 source，并在 RAG 中只作为召回/导航线索，最终回答和引用仍以原文页为准；否则没有可验证来源的总结不应进入政府场景的回答上下文。

该流程解决了两个相反问题：完全忽略历史会导致代词追问失败；把历史拼进检索词又会污染新问题。当前实现采用业内常用的“上下文问题改写 + 独立检索 + 受限生成历史”模式。

## 三、本轮发现并修复的主要问题

| 问题 | 风险 | 处理结果 |
| --- | --- | --- |
| 编译首次成功未将文档置为已发布 | 文档永久停在索引中 | 成功即发布，最终失败才置失败，并新增单测 |
| 编译服务是可选依赖 | 可能静默走空证据路径 | 改为强依赖，启动时即失败暴露配置问题 |
| 大 PDF 独占单个入库 worker | 后续文件长时间停在解析中 | 入库并发隔离，支持配置并发数 |
| 重启恢复会重复解析已分块文件 | 大文件恢复时间过长 | `indexing` 且已有 Chunk 时直接恢复编译 |
| source key 在 ACL 变化后可能过期 | 文档写入旧权限组 | 根据文档所属知识库重新解析当前 source |
| 登录页服务端与客户端初始状态不一致 | React hydration 崩溃，出现页面无法加载 | 统一首屏状态，客户端挂载后恢复会话和路由 |
| 管理接口嵌套对象返回密码哈希或加密密钥 | 敏感派生值泄露 | 使用显式字段选择并统一掩码；接口扫描为 0 个敏感字段 |
| 模型密钥以明文保存在数据库 | 数据库泄露后可直接调用模型 | AES-256-GCM 加密，已有 2 个供应商完成迁移 |
| 行业库创建者和现管理员职责混合 | 创建者转交后仍能维护内容 | 创建者保留设管理员/删除；当前管理员负责内容与授权 |
| 管理菜单仅按角色或仅按关系判断 | 菜单显示与实际资源范围不一致 | 菜单按能力，资源按实际管理关系，服务端逐操作复核 |

## 四、在线预览

在线预览不依赖模拟页面。前端按文件原格式使用成熟组件：DOCX 使用 `docx-preview`，PDF 使用浏览器 PDF 对象，Excel/CSV 使用 SheetJS，图片直接呈现，文本和解析结果提供 Markdown 视图；同时提供原文档、Docling 解析、知识切片和元数据四个视图。

引用和知识库列表均通过受保护的文件接口读取，下载或预览前会再次校验当前用户是否仍有该知识库阅读权限。

## 五、验收证据

- API：6 个测试套件、19 个测试全部通过；ESLint 零警告；Nest 构建通过。
- Web：Next.js 生产构建通过，`/`、`/admin`、`/chat`、`/help` 均生成成功。
- GBrain adapter：TypeScript 构建通过。
- Parser：Python 语法编译通过。
- 生产数据：20 份文档全部为 `published`，无 `parsing`、`indexing`、`failed` 残留；11 个活动 source，24 条 source-document 映射。
- 模型：DeepSeek 对话、SiliconFlow `BAAI/bge-m3` embedding、`BAAI/bge-reranker-v2-m3` rerank 均已实际调用验证。
- 密钥：2/2 供应商密钥已加密保存；管理接口不返回 `passwordHash` 或 `apiKeyEncrypted`。
- 真实闭环：中文 DOCX 上传后约 6 秒发布；提问“公务用车第十四条”正确返回“一车一卡、专卡专用”全文，并生成可点击中文来源，在线预览成功，测试文档随后完整删除。
- 浏览器矩阵：CY、caoyang、zhanglei 三个账号的对话、知识库、知识图谱、主题切换、管理菜单和帮助页通过；无 React page error、无 HTTP 5xx。
- 权限拒绝：zhanglei 虽为行业库管理员，但新增一级组织和新增员工接口均返回 403；其管理后台仅有“行业库管理、权限授权”。
- 运行服务：Web、API、Parser 均为 systemd `active`，健康检查通过。

## 六、与 GBrain 官方建议的符合度

符合项：

- Git/source 仓库保存可恢复的规范知识，索引不是唯一事实源；
- 使用 source 作为检索和共享边界；
- 使用 GBrain 原生同步、混合检索、重排和维护流程；
- 查询宽度按问题类型调整，而不是为“第 N 条”编写特殊规则；
- 共享知识不按用户重复复制，采用共享 source 和增量同步。

项目化增强：

- 官方示例偏静态组织共享，本项目增加组织、角色、人员三类动态授权；
- 官方 frontmatter 主要用于知识语义，本项目不把它当最终 ACL；
- 数据库负责业务主数据和最终权限，GBrain 负责知识组织与检索；
- 权限 source 提供性能和隔离，查询末端 ACL 提供安全兜底。

## 七、后续生产建议

以下不阻塞当前局域网上线，但建议进入下一阶段：

1. 在入口增加 Nginx/Caddy TLS、可信证书和安全响应头策略，禁止直接暴露 3200/3202/8100 端口。
2. 接入政务统一身份或企业 SSO，并增加 MFA、密码轮换和离职账号自动停用。
3. 将 PostgreSQL、Redis、上传原件和 GBrain source 做每日异机备份与恢复演练。
4. 增加 Prometheus/Grafana 或等价监控，覆盖解析时延、队列积压、模型错误率、检索空结果率和越权拒绝事件。
5. 对复杂扫描 PDF 建立独立高内存解析队列；当前 Docling 质量优先模式可能消耗数分钟和较多内存。
6. 在正式大规模使用前执行真实并发压测、长会话压测和 24 小时稳定性测试。
