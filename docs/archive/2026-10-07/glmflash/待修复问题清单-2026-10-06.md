## P0（必须立即修复）

### P0-1　后台 RAPTOR 补嵌任务重抛授权异常，导致整个 API 进程崩溃（已在测试中实际复现）

- **位置**：`apps/api/src/raptor/raptor.service.ts:1065`（catch 块中 `rethrowAuthorizationFailure(err)` 对 403/503 重新抛出）与 `apps/api/src/raptor/raptor.service.ts:1001`（`void this.backfillNodeEmbeddings(kbIds[0])` 无 `.catch` 兜底）；根因辅助条件：`apps/api/src/permission/authorization-revision.ts:67-70`（`rethrowAuthorizationFailure` 对 403/503 re-throw）。
- **机制**：向量检索未命中时（raptor.service.ts:1001）以 fire-and-forget 方式启动后台自愈任务 `backfillNodeEmbeddings`。该任务内部调用 `EmbeddingService.embed → admitModelCall → assertRequestAuthorization`。当执行期间授权 revision 发生变化（任何撤权、授权变更、grant 过期都会 bump revision），`assertAuthorizationSnapshot` 抛出 `ForbiddenException('Authorization changed; retry the request')`。`backfillNodeEmbeddings` 的 catch 块（:1065）调用 `rethrowAuthorizationFailure`，把 403 **再次抛出**——该设计在请求路径上是正确的 fail-closed，但这里是**无人 await 的后台 Promise**，re-throw 直接产生 unhandled rejection，Node（≥15 默认 `--unhandled-rejections=throw`）**整进程退出**。
- **复现**：2026-10-06 在本地测试环境（3202 端口，RLS_ENFORCE=1 + CORE_AUTH_ENFORCE=1）运行 8 模块功能套件的"越权与多租户隔离"模块时，API 进程于 21:16:19 崩溃退出，日志尾部即该异常栈。进程由守护进程自动拉起，但崩溃窗口内所有进行中请求丢失、所有用户服务中断。
- **影响**：生产环境中任何授权变更（管理员日常操作）都可能触发全实例崩溃。多实例部署时全部实例共享同一授权状态表，可能被逐个击倒。
- **建议修复**：
  1. `backfillNodeEmbeddings` 的 catch 不再调用 `rethrowAuthorizationFailure`——后台自愈任务对授权失败应仅记录并静默退出（`backfillInFlight` 已由 finally 清理）；
  2. 排查所有 `void this.xxx()` 形式的后台任务调用点，统一要求 `.catch()` 显式兜底（已核对：`chat-run.service.ts`、`brain-outbox.service.ts`、`ingestion.service.ts:820` 均有兜底，**仅 raptor.service.ts:1001 缺失**）；
  3. 长期：`main.ts` 增加 `process.on('unhandledRejection')` 记录告警而非退出（或至少区分"后台任务异常"与"请求异常"），避免同类问题再次演变为全站故障。

## P1（尽快修复）

### P1-1　自适应检索模式（生产默认开启）下，柔性地板与拒答阈值改动全部失效

- **位置**：`apps/api/src/retrieval/evidence-calibration.ts:16-18`（`calibrateRerankScore` 需要 `RERANK_DEPLOYMENT_REVISION` + `RERANK_CALIBRATION_FILE` 且样本数 ≥200）；`.env.example:246`（`ADAPTIVE_RETRIEVAL_ENABLED=true`）；仓库内**不存在任何校准文件**，`.env.example` 也未配置这两个变量。
- **机制**：自适应模式下 `measuredScoreOf`（`retrieval/score-contract.ts:34-38`）只认 `calibratedProbability`。无校准文件时 `calibrateRerankScore` 恒返回 null → `hasMeasured=false` → `citation-assembly.ts` 的 Top3 平滑分支（:496 `measuredList.length >= 5`）与基于 measured 的地板/保底逻辑全部旁路；`decideEvidenceSufficiency` 走 `scoreCalibrated=false` 分支，拒答门禁 0.40→0.35 的调整同样不生效。单元测试由 `jest.setup.ts` 固定 `ADAPTIVE=0`，测的是另一条路径。
- **影响**：27cd327 引入并默认关闭灰度的"柔性地板"机制，在真正开启自适应的生产实例上从未生效过；运维配置的预期与实际行为不一致。
- **建议修复**：① 生产实例若开启 ADAPTIVE，必须先产出并配置 Platt 校准文件（留出集 ≥200 样本）；② 或明确文档化"无校准文件时柔性地板不生效"，并在追踪中输出 `floorMode=relative|calibrated` 供甄别；③ 为 ADAPTIVE=1 路径补一组单元测试。

### P1-2　AdminGuard 个人知识库创建豁免使用 URL 子串匹配（纵深防御缺陷）

- **位置**：`apps/api/src/auth/auth.guard.ts:53-57`。
- **机制**：`request.url?.includes('/admin/kbs')` 是子串匹配——任何 **POST** 请求只要 URL 中**包含** `/admin/kbs`（如 `/api/v1/admin/kbs/:id/admins`）且 `body.type === 'personal'`，即被判定为"个人知识库创建"而**跳过全部管理员能力检查**。当前 `@Post("kbs/:id/admins")`（admin.controller.ts:2339）等处理器内部有 `canManageIndustryKb`/`isSystemAdmin` 二次校验兜底，未构成直接提权；但任何新增的 `/admin/kbs/*` POST 路由若遗漏内部校验，即成为无权限端点。
- **建议修复**：豁免条件改为精确匹配 `request.path === '/api/v1/admin/kbs'`（与第一个条件一致），删除 `request.url?.includes(...)` 分支。

### P1-3　web lint 失败：109 个 error，其中包含真实功能缺陷

- **位置**：`apps/web`（`pnpm --filter web lint` 退出码 1）。
- **明细**：86 处 `@typescript-eslint/no-explicit-any`（集中在 `src/components/admin/AdminScreen.tsx`(42)、`LibrariesScreen.tsx`(17)、`SystemStatusPanel.tsx`(12)、`OrgPanel.tsx`(12)、`UsersPanel.tsx`(9) 等）；13 处 `react-hooks/set-state-in-effect`；`AdminScreen.tsx:34` "Cannot access variable before it is declared"（effect 引用了在其后声明的 `loadAuditPage`）；`UniversalDocumentViewer.tsx` 3 处 React Compiler 放弃 memoization（依赖数组与推断不一致）。
- **真实功能缺陷（必须修）**：`AdminScreen.tsx:31-36` 审计页懒加载 effect 的依赖数组只有 `[tab]`，但内部判断依赖 `capabilities.includes('*')`。capabilities 若在挂载后异步到达（登录态初始化），effect 已随 tab 变化执行过且 `dreamLazyRef` 已置 true，**超管进入审计页时 Dream 遥测可能永远不加载**。
- **建议修复**：修复懒加载 effect 依赖（`[tab, capabilities]` 并调整 ref 置位时机）；补齐 setState-in-effect 的模式修正；`no-explicit-any` 分批治理并纳入 CI 门禁。

### P1-4　授权 revision 高频 bump 与请求内一致性校验叠加，内容操作风暴期间并发查询大面积 403/404（功能测试实测）

- **位置**：`apps/api/src/permission/authorization-revision.ts`（`readAuthorizationSnapshot`/`assertAuthorizationSnapshot`）；`retrieval/model-admission.ts:16`（每次模型调用前 `assertRequestAuthorization` 重读 `AuthorizationState` 比对 revision）；数据库触发器/协调任务在每次知识库、文档增删改后推进 revision（实测单次文档创建 revision +2，当前值 43k+）。
- **机制**：每个请求在开始时读取授权快照，模型调用准入时再次读取当前 revision 比对，两者不一致即抛 `ForbiddenException('Authorization changed; retry the request')`。当短时间内有大量内容操作（批量入库、并发上传、删除）时，后台访问协调持续推进 revision，使"请求开始 → 模型调用"窗口内 revision 必然变化，**所有携带模型调用的查询请求 403**；分页/列表类读请求的可见性判定同样依赖该上下文，返回 404。
- **实测证据**：2026-10-06 功能套件运行中，模块 D 完成 13 项文档操作后，模块 B 的并发/多轮问答（403×5）、模块 E 的全部检索请求（403×4）、模块 F 的全部分页请求（404×6）在数分钟窗口内连续失败；稳态下（操作停止后）同样的请求全部恢复正常（search 201×3、问答正确返回带引用答案）。9 月 29 日基线运行中 D 模块并发入库用例因超时失败（风暴较弱），故未暴露此问题。
- **影响**：真实生产场景中，批量文档导入/重建索引期间，所有在线用户的问答与检索将不可用（重试也不能恢复，直到风暴结束）。
- **建议修复**：① 快照一致性校验增加小容忍窗口（如 revision 变化但用户未撤权时放行并记审计），或请求开始快照绑定"用户撤权标志"而非全局 revision 计数；② 模型准入失败在 SSE 管线中应显式终止运行并返回错误，而不是落库空答案（见 P2-8）；③ 为内容风暴场景补一条回归测试。

## P2（排期修复）

### P2-0　运行中模型调用失败被静默落库为"空答案"（200 + done）

- **位置**：问答 SSE 管线（`apps/api/src/chat/chat.service.ts`）的模型调用准入失败分支；`chat-run.service.ts:complete`。
- **机制**：功能测试实测：CHAT-001/CHAT-005 在授权 revision 风暴期间返回 HTTP 200、SSE 正常结束、`done=true`，但 `answer` 为空字符串并落库为正式消息。用户看到"回答成功但内容为空"。稳态复测（P1-4 排除后）同一问题正确返回答案，证明是故障路径静默吞错。
- **建议修复**：模型调用准入/生成失败时，要么以 `failed` 终止 run 并给出错误信息，要么输出明确的拒答文案；禁止空答案 + 成功状态落库。

### P2-1　RERANK_MAX_DOCS / RERANK_TIMEOUT_MS 代码默认值与 `.env.example` 不一致（多实例行为漂移）

- `fusion-rerank.ts:322,473` 代码兜底 `RERANK_MAX_DOCS=100`、`RERANK_TIMEOUT_MS=60000`；`.env.example:224,228` 为 `15000/60`。按 example 部署的实例与未配置该项的实例行为不同。建议统一为同一来源（或 example 注释标明"未设置时代码默认 100/60000"）。

### P2-2　chat-run reaper 与流式总时限存在配置耦合

- `chat-run.service.ts:276-283` `reapStaleRuns` 仅按 `startedAt` 判定（默认 10 分钟），不感知活跃租约；`complete()` 又有 `status:'running'` 守卫。默认 `StreamDeadline` 总时限 120s 时安全；一旦运维将流式总时限调高超过 `CHAT_RUN_STALE_MS`，存活中的运行会被误判为 stale 标记失败，最终完成写入被守卫丢弃。建议 reaper 排除"租约仍活跃"的运行，或文档化两者的配置约束。

### P2-3　AuthService.userStatusCache 只增不减

- `auth.service.ts:29-61`：TTL 5s 的进程内缓存，过期项从不删除，Map 随历史用户数无界增长（单条虽小，长生命周期进程仍缓慢泄漏）。建议周期清理过期键或改用 LRU。

### P2-4　HTTP body 上限 250MB 过大

- `main.ts:86-87`：`express.json/urlencoded limit 250mb`。上传接口已用 multer 限制 200MB，JSON 体无需如此宽松，放大内存型 DoS 面。建议按路由区分（普通 JSON 1-10MB，上传专用 multipart 200MB）。

### P2-5　摄取文件名校验的两处小缺口

- `ingestion.controller.ts:41-47`：`decodeURIComponent` 分支只替换 `[\\/]`，未再次剥离控制字符——`%00` 解码为 NUL 后进入 `writeFile` 路径名（Node 报 ERR_INVALID_ARG_VALUE，仅产生报错不构成穿越，但与主分支行为不一致）。另外上传仅按扩展名分类，无 MIME 白名单（内网场景可接受，建议至少对可执行/脚本扩展默认拒绝并文档化）。

### P2-6　`buildContextualizedRerankText` 的三处遗留（27cd327 评审 P2 项仍有效）

- `fusion-rerank.ts:22-46`：① `headingHierarchy` 已在 `retrieval-arms.ts:2103` 透传但本函数未使用（且 `section_rescue` 使用蛇形 `heading_hierarchy`，命名不统一）；② 无结构文档的 `breadcrumb` 默认值 `'文档正文'`（`markdown-chunker.ts`）会被拼进重排文本成为噪声；③ `retrieval-arms.ts:2107` 将整个 `metadata`（含 `contextual_prefix`、表头）挂到候选上，追踪/日志体积无谓膨胀。

### P2-7　`RETRIEVAL_MIN_FLOOR_GROUPS` 显式设置时绕过灰度开关

- `citation-assembly.ts:535-537`：`guaranteeDefault` 已按 `softFloorEnabled` 门控，但环境变量显式设置时无条件覆盖——灰度开关关闭（默认）的实例只要误配该项即提前启用保底机制，与代码注释"guarantees exist only with RETRIEVAL_SOFT_FLOOR_ENABLED"矛盾。建议显式设置时强制要求开关打开，或注释修正。
