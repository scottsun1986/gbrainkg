# GBrainKG 全面审查与 SOTA 优化建议

本报告面向项目负责人，审查知识入库、知识查询、权限管理及页面体验，记录本轮已修复的缺陷，并提出需由负责人决定的后续优化。日期为 2026 年 10 月 1 日。

**结论：项目具备较完整的企业 RAG 架构基础，但目前证据不足以认定达到全球 SOTA。** 优先事项是建立可复现的质量、撤权、延迟和成本评测，在此基础上优化关键路径。本轮修改限于确定的功能缺陷与启动等待问题，没有开启新检索策略、改动生产配置、执行生产迁移或发布。

## 审查范围与证据边界

本轮检查前后端构建、测试、启动数据加载、流式状态、回答 Markdown、反馈、会话切换，以及入库版本发布、检索融合、重排、证据校验、缓存和权限代码。核心文件包括：

- 入库：`ingestion.service.ts`、`document-version-store.ts`、`enrichment.processor.ts`、`external-acl.ts`。
- 检索：`chat.service.ts`、`retrieval-arms.ts`、`hybrid-retrieval.service.ts`、`query-execution.ts`、`citation-assembly.ts`、`semantic-cache.service.ts`。
- 权限：`document-acl.service.ts`、`authorization-revision.ts`、`evidence-dependencies.ts`、`authorization-output.ts` 及隔离库 RLS 验证。
- 页面：`page.tsx`、`useAdminBootstrap.ts`、`ChatScreen.tsx`、`AnswerMarkdown.tsx`、预览、知识库与图谱入口。

验证使用本地工作区、独立前端构建、内存 API 浏览器夹具及专用数据库 `gbrain_core_opt_test`。没有在业务库批量上传测试知识，没有运行默认地址可能指向生产的质量/压测脚本。浏览器夹具验证 UI 与接口契约，不能证明真实模型的回答质量；数据库集成验证生命周期和权限，不能证明百万块容量。既有工作区删除的历史报告和截图保持原样。

这是一轮广泛的代码与回归审查，不是形式化无缺陷证明。未获得本轮真实多领域语料、供应商实际费用和可比较的竞品运行结果，因此不提供项目“全球排名”、虚构准确率或预测性能收益。

## 已修复的确定缺陷

| 缺陷 | 原行为与影响 | 本轮修复 | 验证 |
| --- | --- | --- | --- |
| API 构建范围错误 | 根目录 `perf-probe.ts` 被默认纳入 `rootDir=src` 编译，报 TS6059，`pnpm test` 在构建阶段退出 | 构建明确只纳入 `src/**/*.ts` | 完整构建和测试 |
| 管理员首屏被全量管理数据阻塞 | 轻量 bootstrap 后仍 `await admin/data`，登录状态迟迟不能进入主壳 | 管理数据后台补齐；使用请求序号和当前 token 检查阻止过期响应写入共享状态；失败提供提示 | 人为延迟管理接口 3 秒，主壳在接口完成前可操作 |
| 停止回答不能正确收尾 | 切换 streaming 状态后 effect 清理使末次 flush 失效，回答可能一直显示生成光标，缺少操作按钮 | 用户停止前同步冲刷缓冲并将回答标为完成 | 实际分段 SSE 浏览器验证 |
| 新建会话被历史请求覆盖 | 新建会话未使历史读取序号失效，旧网络响应到达后填回旧消息 | 新建会话使在途历史响应失效并清理加载状态 | 慢历史请求与新建会话并发验证 |
| 反馈失败仍显示成功 | 未检查读取会话及反馈 POST 的 HTTP 状态，失败被吞掉 | 校验状态，提交失败明确提示 | 反馈 API 故意返回 500 |
| 多轮实时回答反馈定位错误 | 流式回答没有持久化消息 ID，较早回答按钮回退查最后一条消息 | 服务端落库后在 done 返回 `message_id`，前端绑定对应回答 | 服务端契约单测；两轮回答后点击第一条反馈 |
| 查询范围更新错误 | 只以可见库数量作为 effect 依赖，数量不变而 ID 更换时保留旧库；刷新也可能覆盖用户自选范围 | 按可见库集合更新，保留有效自选范围；原为全选时跟随新集合；会话列表在数据应用完成事件后刷新 | 同数量替换知识库的浏览器验证 |
| 任务列表排版重复 | 当前 marked 会产生 checkbox token；渲染器已画复选框又把 token 原文回退输出为 `[x]` / `[ ]` | 忽略已由列表项呈现的 checkbox token | 新增真实 React 渲染回归及四种尺寸/主题排版验证 |

修复没有添加部门、考勤、排班等业务同义词或加权分支，没有调整检索阈值和权限语义。消息 ID 是兼容性的 done 扩展字段，旧客户端可忽略。旧服务端未返回 ID 时前端仍有兼容回退，因此上线时应同步更新 API 与 Web；历史无 ID 的前端状态不能靠该字段回溯补齐。

## 页面加载与查询体验

### 已有优势及本次实测

知识库、图谱、管理、设置和原始文档预览已采用动态分包；聊天历史回答组件采用 memo；流式增量约 50ms 合并；历史切换采用 transition。启动已有轻量 session/bootstrap，并行读取会话列表；本轮移除了后续管理全量请求的等待。字体样式使用非阻塞加载和回退字体。

浏览器在本地生产构建、1440×1000 窗口、外部字体不可达、管理数据额外延迟 3000ms 的条件下，修复后的主壳可操作时间实测为 **2822ms**，且管理接口尚未完成。这是一次本地夹具测量，含冷加载与自动化路由开销；没有同条件旧版时间分布，不能换算为生产提升百分比，也不能当作 LCP 或 P95。完整结果在 `docs/validation/project-audit-20261001/browser-results.json`。

回答排版验证覆盖 1440、390、320 像素及移动深色模式：标题/段落/嵌套列表/引用正确呈现，行高与间距合格，表格和代码内部可滚动而不撑宽页面；代码里的引用不会变按钮，恶意 HTML 不会执行。人工检查移动深色截图另发现并修复任务标记重复。排版截图在同目录。

### 仍有优化空间

1. **登录首屏等待会话列表：已落实后续修复。** session 独立完成后即可进入主壳，会话异步加载；请求有独立超时，新加载及卸载会取消旧请求，迟到结果受令牌和请求序号约束。双接口延迟 3 秒的浏览器回归通过，详见后续优化验证记录。
2. **登录静态引入 ChatScreen：已落实后续修复。** ChatScreen 改为按需分包，浏览器验证未登录页面没有下载聊天渲染代码。真实用户 LCP/INP 收益尚待采集，不能由分包本身推出改善百分比。
3. **长会话读取和渲染缺少分页。** `ConversationController.get` 一次返回整段消息，逐个不同 dependencyManifest 验证权限；前端挂载全部消息及 trace。建议游标分页、trace 按需读取、批量证据校验和消息虚拟化；必须保留撤权检查与引用体验。
4. **已访问屏幕常驻会占用内存。** 状态保持有价值，但复杂图谱、预览和大列表应暂停隐藏状态下的计算，建立页面驻留上限。不要仅以隐藏 DOM 推断无 CPU/内存成本。
5. **真实 Web Vitals 尚缺本轮证据。** 建议按页面/角色/设备/网络分别采集 LCP、INP、CLS、JS 体积、长任务和请求瀑布，区分冷/热缓存。Google 的建议良好阈值为第 75 百分位 LCP≤2.5s、INP≤200ms、CLS≤0.1；应由真实用户或相应实验测量，不能由构建耗时代替。[Web Vitals](https://web.dev/articles/vitals)
6. **检索速度与生成速度分开看。** `quality-first` 的检索预算分别为 30/60/90 秒，fast 路由也会提升为 standard。严格输出模式还会缓冲完整内容后做权限许可再发送。二者都有合理安全/精度目的，但可能让用户长期看不到可读回答。建议独立展示真实阶段进度，统计首个状态、首个可读文本、最终答案时间；禁止以降低权限检查换取速度。

## 核心流程合理性

### 知识入库

现有流程包括解析回退与质量检查、内容/解析器指纹缓存、分块、向量与词法索引、不可变版本与 generation 发布、outbox 及后台富化。核心索引与辅助图谱/摘要工作分离的方向合理。版本发布以 ready/expected 覆盖数和 manifest 检查阻止半成品切换，旧版可保持在线，乱序和重复事件受到栅栏限制。本轮真实数据库验证了版本切换与回滚、旧版可用、差量图谱及并发更新。

需要继续验证：复杂 PDF/OCR、跨页表格、PPT 图表、公式和扫描附件的原文定位；截断是否明确显示；失败重试、毒任务、队列积压和源删除传播；跨进程解析缓存的来源权限隔离；连接器断线时内容与 ACL 的一致性。不能把“published”单一状态当作所有富化完成。

建议：用状态页明确“已接收→解析→质量检查→核心索引可查→辅助富化”，展示当前可检索版本与失败阶段；按文件类型构建有页码/框选区域/表格单元格金标准的解析回归库。保留原文、块、索引、派生摘要的分层，避免把 LLM 生成的上下文当成原文证据。

### 知识查询

现有路径具备密集向量、全库词法 BM25、图谱、可选 BGE-M3 learned sparse/MaxSim、RRF 融合和统一重排；还有查询改写、探针、多跳补检索、父块/邻域、上下文预算、数字/极性与蕴含验证、引用回绑、精确缓存和负反馈案例。总体方向合理，符合 corpus-agnostic 约束。

风险主要来自链路复杂度及收益证据：多路候选、探针、重排与校验的累积成本可能很高；结构性短查询不一定是简单题；词面证据检查可能误伤语义等价回答；图谱/摘要召回不能自动等于证据完整；rerank score 不是天然置信概率。现有模型修订绑定校准和失败降级监测有价值，需要验证真实启用状态。

审计时 `calibrateRerankScore` 逐次同步读取和解析校准文件。后续已加入单条配置缓存，检查文件标识、大小及纳秒时间戳以立即识别替换或删除；100 次评分仅读取一次配置的回归通过。每次调用仍检查文件元数据，真实高并发开销尚待测量。模型/修订绑定仍保留，样本量和语料/验证集标识校验已加强。`chat.service.ts` 的编排仍较大，建议后续围绕计划、召回、证据包、输出拆分职责，同时保留当前安全屏障和契约测试。

建议保留 dense+BM25+graph+reranker 基线，以同语料、同权限、同成本口径逐个消融 sparse、MaxSim、late chunking、上下文前缀及多跳；只有证据覆盖不足才增加轮次。对比较、表格计算、全量清单、版本冲突设置通用任务契约：列出缺证字段，明确样本不完整，不把 TopK 结果当全量计数。

### 权限管理

现有权限包括用户/角色/组织、知识库、文档 inherit/restricted、请求身份上下文、数据库 RLS、主库授权 revision、证据来源合取、缓存依赖重验、历史回答来源失效处理、模型调用前授权及输出屏障。空 restricted ACL 不应被理解成继承；当前代码有显式模式。连接器未映射/不可验证 ACL 默认收紧，方向合理。本轮真实 NOBYPASSRLS 权限矩阵及撤权与严格输出序列化验证通过。

仍需真实连接器验证“源权限变更→本地 ACL→所有派生物/缓存/预览→历史回答”的传播时延和失效行为。本地 ACL 映射不等于自动实现所有源系统共享语义。普通流式输出已经发送的文字无法事后撤回；严格缓冲模式增强撤权保证但牺牲首字体验，须明确产品契约。还应验证应用运行角色、后台服务权限边界和多实例 DB/Redis 配置，而非仅依赖代码开关。

## 供负责人决定的优化路线

以下都尚未自动实施；成本为相对工程复杂度估计，不是报价。

| 优先级 | 建议与结果 | 成本 | 验收及取舍 |
| --- | --- | --- | --- |
| P0 | 建立冻结语料与评测记录，质量/权限/时延/成本统一门禁 | 中 | 独立开发/验证/盲测集合；模型修订、语料及工作树 hash、权限范围可追溯；任何越权失败 |
| P0 | 真实连接器撤权与源删除回归 | 中高 | ACL 新增/收紧/删除/断线/群组变化，验证检索、图谱、缓存、预览、历史及后台派生；先定义撤权 SLO |
| P1 | 关键路径提速，session 先行、会话后补、管理按页加载、长历史分页 | 中 | 低端设备和弱网测主壳、LCP、INP；慢请求不能冻结输入；分页不能绕过权限 |
| P1 | 证据充分性驱动的自适应检索和模型校准 | 高 | 配对消融质量非劣、尾延迟与成本下降；新增分支必须通用；不能用少量固定业务题调到过拟合 |
| P1 | 可见的证据可信度与失败状态 | 中 | 显示有效版本/日期/原文定位，区分拒答、无证据、服务错误；部分答案要明确缺证部分；不给未校准的“置信百分比” |
| P1 | 复杂解析与表格证据专项 | 高 | 真实文档的 OCR、单元格、公式、跨页、bbox/span gold；输出页/区间可点击核验 |
| P2 | 源端原生连接器与完整身份同步扩展 | 高 | 按最重要的业务源逐一验收；先做好一个连接器的权限语义再扩数量 |
| P2 | 百万块和十实例容量验证 | 高 | 共享 PostgreSQL/Redis/Parser/MinIO/Nginx；实例专属库及 Redis DB；多实例混合入库/检索测吞吐、公平性与恢复 |
| P2 | 图谱/late interaction/新模型升级 | 中高 | 每项单独 A/B 或 shadow；实际收益不足则不扩大启用；保留当前混合检索基线 |

建议先选择 P0 与关键路径提速，之后才投入新模型和额外检索机制。无需为追求 SOTA 重复拉起中间件，也无需立即替换 PostgreSQL。

## SOTA 目标的可检验定义

全球企业知识库没有覆盖所有场景的单一可信排行榜。应先声明项目目标场景、语种、文档类型、规模和部署成本，再与可复现基线比较；对商业产品没有同条件测试就不能声称领先。

建议复用 `tests/evaluation/core-flow` 的配对门禁：至少 1000 题、每桶至少 50 题，冻结测试集、配对 bootstrap 与置信区间；明确 1 个百分点质量非劣下界，质量与引用绝对阈值按该门禁执行。质量样本至少覆盖事实定位、改写、中英跨语种、多跳、跨文档、表格/聚合、完整清单、时间/版本、冲突、无答案、撤权与恶意输入。人工盲评覆盖正确性、事实完整性、引用支撑及可读性；不以关键词出现次数作为最终质量。

- 检索：Recall@K、nDCG@10、MRR、事实与证据覆盖；按查询桶和权限过滤强度分层。
- 回答：正确性、faithfulness、引用 precision/recall、span/bbox 定位准确率、拒答/澄清适当性。
- 权限：跨库/跨用户/跨实例、撤权/有效期/源不可用、缓存/预览/派生摘要/历史/外部模型调用；任何越权为硬失败。
- 性能：真实首个状态、首个可读文本、最终答案 P50/P95/P99，冷/热缓存及错误/降级率；配对门禁要求 P95 与总成本分别下降 25%，这是项目目标而非本轮已实现收益。
- 成本：记录供应商实际 usage 与费用，缓存计费、解析/索引/存储/共享资源摊销；估计 token 不能冒充实际账单。
- 规模：10 万块/20 并发、100 万块/50 并发、10 实例混合任务；ANN 在可见比例 100%/10%/1% 下对照精确搜索。

该评测契约是可追求和审计的 SOTA 路线；测试脚本存在或 selftest 通过，都不等于这些指标已经达标。
