# 会话并发与按需加载修复（2026-10-05）

## 架构判断

当前前端已经使用“提交问题后立即返回 runId，再按阶段轮询”的后台任务模式，不需要为多会话并发重写传输协议。任务结果保存在数据库，不依赖正在显示的会话，也不需要为每个会话保持 SSE 连接。保留这一模式，可直接复用后台运行状态、取消接口和完成结果。

原实现已经有按会话索引的运行注册表，但实际视图归属与取消生命周期没有完整遵守这个边界：

- 新会话 A 的 POST 响应迟到时无条件切换当前视图，会覆盖用户已打开的 B。
- 停止当前会话时遍历所有轮询器，连带停止其他会话的客户端进度维护。
- 切回正在运行的会话时，把尚未保存的回答视为中断，显示已经完成的错误占位。
- 刷新后只有阶段名称，没有 runId，也没有恢复轮询；旧 bootstrap 快照还能删除本地正在运行的记录。
- 完成结果只写入全局引用列表，未绑定到对应回答的 sources，答案角标和来源按钮缺失。
- 历史窗口从最早消息开始，长会话的最新问题不在首屏；诊断和预览已有延迟加载，Markdown 解析仍随初始页面加载。

## 修复边界

`ChatScreen.tsx` 复用一个共享的轮询生命周期，每个会话独立持有停止函数、runId、阶段和重试定时器。收到 POST 响应时，只在原草稿仍拥有当前视图时切换到服务器分配的会话 ID。其他会话继续运行，停止按钮只取消当前会话。相同会话已有运行时立即拒绝第二次提交；`applyPoll()` 比较 runId，防止旧轮次的迟到响应覆盖新轮次。

运行完成后，结果和 sources 一起绑定到对应回答。后台完成的会话记录只保存终态 ID，不缓存来源正文。再次打开会话从服务器重新读取经过授权校验的消息；若完成状态与历史快照竞争，仅重新读取一次，不能以浏览器缓存覆盖服务器隐藏的失效来源。

会话列表通过现有批量查询附带 runId；选中的会话通过现有详情查询附带 activeRun。恢复任务不为每条历史会话获取完整答案或诊断链路。阶段轮询在隐藏页面放缓到 8 秒，但继续维持后台任务的客户端租约。

## 加载与交互

进入空白问答页面不加载历史正文。只选择会话后加载最新 50 条；“加载更早消息”按游标再取 50 条，按消息 ID 去重并保留当前正在生成的占位。详情接口采用倒序查询并恢复显示顺序，通过多取一条判断是否还有历史，避免额外全量 COUNT。切换会话取消旧历史请求，慢响应不能覆盖新视图。

输入草稿按会话暂存，切换回来可继续输入。历史加载时禁止提交到尚未完成加载的会话。新回答生成期间可新建另一会话并提交问题。Markdown 组件改为按需动态加载；文档预览和单条 trace 保留现有按需加载方式。完成回答的长文本不按 token 高频重复解析。

这些修改没有增加状态管理依赖、传输模式或新的后端服务。消息详情的首个窗口改为最新消息，`before` 游标表示继续读取更早消息；保留原返回字段并新增可选 activeRun。

## 验证与限制

定向验证由 gpt-6-luna 执行：运行注册表旧 runId 迟到拒绝、会话详情最新窗口与 cursor、错误状态持久化，以及前端类型/静态检查。浏览器验证需要覆盖 A 迟到响应不切走 B、A/B 独立完成、停止 B 不影响 A、刷新恢复正在运行的会话、历史正文和 trace 按需加载。最终执行结果见下节。

本次没有运行新的全量测试，也没有部署生产。并发会话的正确归属不等于后端模型供应商能够无限并行；检索和模型调用仍受现有后台配额与执行预算约束。

## 交互参考

[Microsoft Copilot 官方历史说明](https://support.microsoft.com/en-us/microsoft-copilot/conversation-history-in-microsoft-copilot)展示通过会话历史重新打开既有对话的交互。本次沿用会话侧栏和选择后加载正文，不宣称该产品提供与本项目相同的并发任务功能。

[MDN 的 SSE 说明](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)记录 HTTP/1 下浏览器每域名通常最多 6 条 SSE 连接。现有后台 runId 轮询已符合本项目的并发需求，因此无需新增多个常驻 SSE 连接；该限制不适用于同等方式的 HTTP/2 连接协商，不能笼统宣称所有流式传输都慢。


## 最终定向验收

前端 TypeScript、ChatScreen 与运行注册表的 ESLint、Next 构建通过；运行注册表 11 项回归通过。Playwright 在本地 3200 使用受控 API 响应完成以下验收，没有调用模型供应商，也没有写入真实业务数据：

- A 的提交响应延迟时仍能提交 B，两者分别轮询；A 的迟到响应不切换 B 的视图。
- 停止 B 时 A 仍在运行，只有 B 收到取消请求；停止后 A 的轮询计数继续增加。
- A 后台完成不会把回答写入 B；重新打开 A 从服务器取得 A 的回答。
- 刷新前后比较新的轮询计数，确认通过服务端活动任务信息恢复 A，而不是把旧请求记录误当恢复成功。
- 历史首个窗口请求 `limit=50`，下一页才携带 `before`；重叠边界消息不重复，运行中的占位仍保留。
- 展开历史回答前没有 trace 请求，展开后才请求对应消息的 trace；无页面 JavaScript 错误。

结果保存在 [浏览器结果 JSON](chat-concurrency-browser.json)、[构建与验收摘要](chat-concurrency-browser-validation.md)及 [分页截图](chat-concurrency-history.png)。测试响应覆盖状态竞争和交互契约，真实模型答案由单题 API 验证，不能把 stub 验证描述为模型精度测试。

此次还定位了测试运行目录差异：3200 使用 `NEXT_DIST_DIR=.next-live`，普通构建写入 `.next` 不会更新该服务。已按实际运行目录重新构建并更新本地测试服务，确认被服务加载的 JS 与新构建哈希一致；旧生成目录已备份。未修改应用源码来绕过旧构建问题，没有操作生产服务。后续测试必须同时记录运行目录与实际服务的构建指纹。
