# 低分排除优化落地评审（27cd327）

> 评审对象：`docs/retrieval-low-score-exclusion-optimization-proposal.md` 与提交 `27cd327 feat(retrieval): 优化候选饱和下的低分排除机制与重排上下文增强`
> 方式：只读代码与配置分析，未改代码，未连接测试或生产环境。
> 已核实：`npx jest src/chat src/retrieval` 共 65 个套件、624 个用例通过（另有 1 个套件、5 个用例跳过）。
> 未核实：生产 `.env` 的实际取值、改动后的线上效果、真实延迟。下文凡是依赖运行时配置的结论都写明了前提。

## 1. 结论

方案对问题的诊断基本正确，但落地版本没有达到方案目标，还带来了新的风险。

1. **核心算法在推荐配置下不会生效。** `.env.example` 打开了 `ADAPTIVE_RETRIEVAL_ENABLED=true`，仓库里却没有重排校准文件。这种情况下 `calibratedScoreOf` 恒返回 null。于是"自适应柔性地板"的平滑分支不会执行，拒答阈值从 0.40 降到 0.35 也不起作用。单元测试是在 `ADAPTIVE=0` 下跑的，所以测到的是另一条路径。
2. **证据筛选把不同量纲的分数放在一起比较**（存量缺陷，这次改动把它放大了）。分组分数 `g.best` 按最大值归一化，地板却锚定在原始或校准分上。超出重排容量、没被重排的候选带着 0.70–0.95 的合成分，归一化后接近 1。它们会占掉新增的 6 个保底名额，并在 MMR 中排在前面。
3. **地板实际上被关掉了。** 普通问题默认 `maxGroups=8`，其中 6 组无条件保底，阈值 `0.10` 还是相对值。再加上地板比例降到 0.22，可以认为相对地板已经不再过滤。提交里的上限常量 `0.28` 永远不会被触发。
4. **流程没有走完方案自己定的 Phase 1。** 没有收集 badcase，没有跑 A/B 评测（`tests/evaluation/results` 里最新的报告是 2026-09-27），也没有补上候选淘汰的追踪。考勤诊断文档已经指出"追踪无法区分 V2 在哪一步被淘汰"，这次是在缺少观测的情况下调的参数。
5. **方案里最有价值的梯度四没有落地**，即两阶段级联重排（MaxSim 粗排后再用 Cross-Encoder 精排）。实际改法是把 Cross-Encoder 的容量从 60 提到 100，代价是延迟和超时风险上升。

建议：先修第 2 节的 P0 和 P1 问题，补上漏斗追踪和评测门禁，再决定这组参数默认值是否保留。**在此之前不要发布生产。**

## 2. Bug 与缺陷（按严重度）

### P0-1　自适应模式下，柔性地板与拒答阈值的改动都不生效

- 位置：`chat/retrieval-arms.ts:252` `calibratedScoreOf`；`retrieval/evidence-calibration.ts:17-18`；`.env.example:221`
- 机制：`ADAPTIVE_RETRIEVAL_ENABLED=true` 时只认 `calibratedProbability`。这个值又要求 `RERANK_DEPLOYMENT_REVISION` 和 `RERANK_CALIBRATION_FILE` 都存在，并且样本数不少于 200。仓库里没有校准文件，`.env.example` 也没有配置这两项。
- 后果：
  - `hasCalibrated=false`，所以 `rawBest = max(g.best) = 1`，Top3 平滑分支被跳过，`effectiveFloor` 退化成"相对比例 0.22"。也就是说，自适应模式下所谓的"柔性地板"只是把比例从 0.35 改成了 0.22。
  - `decideEvidenceSufficiency` 走 `scoreCalibrated=false` 的分支，0.40→0.35 的改动对拒答没有影响。
  - 单元测试由 `jest.setup.ts:25` 固定为 `ADAPTIVE=0`，测的是非自适应路径。
- 建议：先确认生产各实例 `ADAPTIVE_RETRIEVAL_ENABLED` 的实际值。如果是开启的，要么补上留出集 Platt 校准文件，要么承认当前地板就是相对比例，并在追踪中写明 `floorMode=relative|calibrated`。两种模式各补一套测试。

### P0-2　证据筛选混用两种量纲，没被重排的合成分候选会占掉保底名额

- 位置：`chat/citation-assembly.ts:364,437`（`norm` 和 `g.best`），`:449-463`（地板），`:484-492`（保底组）
- 机制：
  - `g.best = raw / max(raw)`。这里的 max 取自全部候选，包括超出重排容量的 `rerankSkipped` 候选。这些候选的合成分是 0.70–0.95（`chat.service.ts:1541`）或 0.92（`section_rescue`）。
  - 非自适应模式下，地板锚定的是原始重排分 `rawBest`，却拿去和归一化后的 `g.best` 比较。
  - 当重排最高分偏低（例如 0.4），而池里有合成分 0.95 的候选时，合成候选的 `g.best≈1`，真正重排过的候选反而被压低。
- 新提交的影响：`guaranteedKeys` 按 `g.best` 取前 6 组。没经过 Cross-Encoder 的候选会优先拿到保底名额，在 MMR 里也占优。提交的本意是保护低分真答案，实际效果可能是保护了没被打分的候选。
- 建议：分组分数只用同一种量纲。可以把 `rerank` 来源和 `synthetic` 来源分成两个池：地板和保底只作用于前者，后者按原始名次补位，并设名额上限。保底的 `minViableRelevance` 应该用原始重排分来比较。

### P1-1　地板基本失去过滤作用，噪声通过 MMR 的固定加分进入上下文

- 普通问题 `maxGroups=8`，保底 6 组，比例 0.22，阈值 0.10 还是相对值。凡是不低于最高分 10% 的候选几乎都能进入候选池。
- MMR 的打分是 `value = 0.72*best - 0.28*redundancy + novelDoc 0.15 + concrete 0.15 + table 0.10`（`citation-assembly.ts:600` 附近）。这些加分是固定值，不随分数缩放。
- 举例：一个 0.12 分、来自新文档的表格块得 0.486；一个 0.50 分、来自已选文档的正文块约 0.51，再扣去冗余惩罚就可能更低。地板放宽以后，低分噪声会凭加分挤掉中高分证据。
- 建议：把加分改成乘性（例如 `best*(1+boost)`），或者只在 `best` 已经超过地板时才加。另外补一个"噪声注入"测试：0.12 分的新文档表格块不应挤掉 0.5 分的同文档正文块。

### P1-2　`RETRIEVAL_MAX_FLOOR_CUTOFF=0.28` 是死代码，平滑公式几乎没有作用

- `baselineScore ≤ rawBest ≤ 1`，所以 `baselineScore*0.22 ≤ 0.22 < 0.28`。只要重排分在 0–1 之间，这个上限永远不会触发。
- `baselineScore` 下限是 `0.8*rawBest`，平滑最多只能把地板压低 20%（0.216→0.172）。方案里说的"分位数锚定"实际上并没有实现。
- 两个新测试都区分不出平滑和保底的作用：
  - 用例一只有 3 条，不满足 `≥5` 的条件，平滑分支没有执行。0.25 本来就高于 0.216。
  - 用例二里 0.22 本来就高于平滑后的地板 0.199。
  - 即使删掉平滑和保底，两个测试仍然会通过。
- 建议：删掉或重新设计这两处逻辑。补边界测试：设置 `rawBest=0.98`、真答案 0.15，并且只能靠保底入池；断言去掉保底以后测试失败。

### P1-3　Token 预算一旦超出就终止整个 MMR 循环（方案根因 5，没有修）

- `citation-assembly.ts` MMR 循环里的 `if (selected.length>0 && usedTokens+groupTokens>tokenBudget) break;`。
- 只要遇到一个大分组，后面能放进预算的小分组（往往就是短事实答案）全部被丢掉。这正是方案描述的场景，提交没有处理。
- 建议：改成跳过当前组继续往下选（`continue`），或者把大组降级为只放 `bestMember`。

### P1-4　语义缓存版本没有更新，旧管线生成的答案会继续回放

- 检索行为变了，但 `SEMANTIC_CACHE_KEY_VERSION`（`.env.example:148`，键构造在 `retrieval-arms.ts:240`）没有更新，TTL 是 24 小时。旧管线中被漏掉证据的答案（非拒答类，会被缓存）会继续回放给用户，评测也会受影响。
- 建议：凡是改动检索默认值，都在发布清单里强制更新缓存版本。更好的做法是把检索配置的哈希放进缓存键。

### P1-5　代码默认值与 `.env.example` 不一致，多实例下行为不可预期

- 代码默认值改成了 0.22 / 100 / 30 / 0.35，但 `.env.example:183` 仍是 `RETRIEVAL_RELEVANCE_FLOOR_RATIO=0.35`，`RERANK_TIMEOUT_MS=15000`，代码兜底却是 60000。
- 照 example 部署的实例仍是 0.35；没写这一项的实例变成 0.22。同一版本在不同实例上的行为不同，排查时很难还原。
- `.env.example` 本身还有重复键：`RAPTOR_ENABLED` 第 110 行和第 173 行，`BGE_M3_HYBRID_ENABLED` 第 198 行和第 223 行。

### P1-6　重排容量 60→100 增加了整轮重排失败的风险

- 一个问题最多会调 3 次 `rerankPool`（`chat.service.ts:3427,3528,3827`），外加每个探针组各一次，每次最多 100 篇、每篇 3000 字符。
- 超时会走 fail-open（`fusion-rerank.ts:572`）。整轮退回合成分以后，自适应校准和拒答门禁都会降级。
- 结果是：容量加大后每个请求更容易超时，超时后精度反而比原来的 60 更差。
- 建议：落地方案里的梯度四（见 3.2）。至少要统计每次重排的 P95 耗时和超时率，按实例给出推荐值。

### P2　其他问题

- `buildContextualizedRerankText` 把文本字段的优先级从 `evidence||snippet` 改成了 `snippet||context||evidence`（探针组路径），这个行为变化没有说明。如果引擎返回的 `snippet` 是截断预览，重排看到的文本会变短。
- 回退臂的 `evidence` 已经带了 `【第X章】【第X条】` 前缀，层级里又追加一次 `articleNo`，条款号重复出现。没有结构的文档 `breadcrumb` 默认是 `'文档正文'`（`markdown-chunker.ts:372`），会作为噪声拼进重排文本。
- 新增透传的 `headingHierarchy` 在 `buildContextualizedRerankText` 里没有用到。`section_rescue` 用的是蛇形命名 `heading_hierarchy`，两种命名不统一。
- `retrieval-arms.ts:2107` 把整个 `metadata` 挂到候选上，里面包括 `contextual_prefix` 和表头。对象变大，追踪和日志的体积也随之增加。只透传需要的字段即可。
- `RETRIEVAL_MIN_FLOOR_GROUPS` 一旦显式设置，就会覆盖 `hasSubQueries ? 0` 的判断，多跳问题也会套用保底，和注释说的不一致。
- 重排缓存键 `candidateHash` 只包含 evidence 文本，不包含重排输入格式的版本。格式变更后，进程内缓存会在 TTL 内返回旧排序。影响不大，但说明"重排输入"缺少版本概念。

## 3. 架构优化建议

### 3.1 统一的"分数契约"

这次的问题，以及方案中的根因 1、2、4，归根到底都是分数含义不清：同一条链路上并存 RRF 分、min-max 合成分、救援常量 0.92/0.96、原始重排分和 Platt 概率，比较时只靠 `scoreSource` 字符串和局部判断。

建议在 `retrieval/` 下定义统一的候选打分结构 `ScoredCandidate { ordinal: rank, measured?: {kind:'rerank', raw, calibrated?}, provenance }`，并遵守三条规则：

- 排序只看名次。
- 阈值只作用于 `measured` 分数。
- 合成分只能用来补位，不能参与和阈值比较的逻辑。

`selectEvidence`、`decideEvidenceSufficiency`、`assessWeakEvidence` 共用这一份契约，消除 P0-2 这类量纲混用。

### 3.2 两阶段级联重排（方案梯度四，建议作为主线）

`hybrid-retrieval.service.ts:143` 已经实现了 BGE-M3 MaxSim，但 `.env.example:224` 里 `BGE_M3_MAXSIM_ENABLED=false`，`BGE_M3_HYBRID_ENABLED=false`。也就是说，方案里提到的学习型稀疏召回和延迟交互在默认配置下都没有启用。

建议改成：RRF 取 Top 150–200，用 MaxSim 粗排到 Top 40，再交给 Cross-Encoder，并把 `RERANK_MAX_DOCS` 回调到 40–60。这样同时解决根因 2（容量截断）和 P1-6（超时），不会靠堆容量换召回。在 MaxSim 未启用时，可以按 RRF 名次截取并保留各通道的头部候选（每个通道的前 k 名必定入池），以缓解根因 1 中单通道强语义命中被稀释的问题。

### 3.3 来源多样性优先于放宽地板

生产中真实出现的漏答案例（考勤 V2）表明，问题出在单一来源独占上下文，而不是低分。两份制度都在候选池里，最终只引用了一份。放宽地板对这类问题没有直接作用。

建议在 MMR 阶段加入通用的"同主题多来源覆盖"约束：如果某文档有一个分组的分数不低于最高分的 X%，并且和已选内容讨论的是同一主题、来源却不同，就至少保留它的 `bestMember`。生成提示词中也要求模型对多份来源的差异和覆盖缺口作出说明。这个做法不依赖业务规则，符合 AGENTS.md 中禁止业务硬编码的要求。

### 3.4 关于小到大上下文增强

方向是对的，但目前只在重排阶段拼接标题和层级。建议：

- 入库时，如果文档结构完整，就跳过上下文前缀（`contextual-retrieval.ts:200-221`），从而节省 LLM 成本。这时重排阶段的层级拼接就成了唯一的补偿手段。它需要和入库阶段的策略保持一致，并把具体做法写进文档。
- 把重排文本的格式版本 `RERANK_TEXT_FORMAT_VERSION` 加入重排缓存键和评测报告元数据，避免格式调整后无法归因。
- 层级只拼接有意义的部分，过滤 `文档正文`、`Default` 等默认值，并对已经存在的章、条前缀去重。

### 3.5 精简 ChatService 与配置项

`chat.service.ts` 的规模接近 6000 行，同一类候选映射代码（docTitle、sectionGroup、section、breadcrumb……）复制了 3 处（1543、1606、2737）。这次新增字段也要同步改 3 处，遗漏是迟早的事。建议抽出 `toCitation(fb)` 作为唯一的映射入口。

检索相关环境变量已有几十个，代码和 `.env.example` 各维护一份默认值。建议改为单一来源：用一个带类型校验的 `retrieval-config.ts`，启动时打印生效的配置哈希，并写入追踪和评测报告。

## 4. 流程优化建议

1. **先观测，后调参。** 在 `evidenceSelection` 追踪里，为每个被淘汰的候选记录 `docId / chunkId / 名次 / 分数来源 / 淘汰阶段`。淘汰阶段可取 `rerank_cap / floor / mmr_budget / max_groups / acl`，只保留前 N 条，并做脱敏。没有这些数据，就无法验证这次改动解决了"真答案被误杀"。考勤诊断已经卡在这一步。
2. **把方案 Phase 1 的评测门禁补上。**
   - 用 `tests/evaluation/quality-gate.ts` 和 `ab-gate-runner.ts` 做新旧两组配置的 A/B 对比，指标包括 Hit@5、MRR、Context Recall、Faithfulness、拒答率，以及 P95 延迟和重排超时率。
   - 方案中引用的 `pytest tests/evaluation/test_retrieval_quality.py --golden-file=...` 文件确实存在，但需要确认是否支持 `--golden-file` 参数。
   - 结果写入 `docs/validation/`。
3. **组织 badcase 回归集。** 把考勤 V2 漏引这类真实案例去标识化后，用 `ingest-bad-case.ts` 加入回归集，作为放宽地板、多来源覆盖等改动的验收样本。
4. **用功能开关灰度发布。** 新的地板逻辑用 `RETRIEVAL_SOFT_FLOOR_ENABLED` 开关控制，默认关闭。先在一个实例上打开对比，再推广。不要直接修改代码默认值，因为修改默认值会在所有没有显式配置的实例上悄悄生效。
5. **发布清单补充以下几项：**
   - 检索行为变化时更新 `SEMANTIC_CACHE_KEY_VERSION`。
   - 同步更新 `.env.example`。
   - 校验各实例生效配置的一致性。可以在 `deploy-prod.sh` 预检中对比各实例的检索配置哈希。
6. **测试同时覆盖两种模式。** 涉及分数的用例，在 `ADAPTIVE=0` 和 `ADAPTIVE=1`（有校准和无校准）下各跑一遍，并加上"去掉新逻辑后测试必须失败"的对照断言。

## 5. 体验优化建议

- **区分拒答的原因。** 快速拒答在置信度降级时有警告追踪，但用户看到的都是同一句标准拒答。建议按原因区分提示文案：确实没有相关资料、相关资料置信度低、部分资料无权限访问。最后一种不能泄露任何具体内容，只说明"可能存在你无权访问的资料"，并且要经过安全评审确认后再上线。
- **说明多来源的差异和覆盖范围。** 当上下文中有多份同主题文档时，回答末尾标出"另有《X》对此有不同或补充规定"，或者说明"以下资料未覆盖 1–30 分钟迟到的处理"。这与 3.3 配套，能直接解决考勤案例的体验问题。
- **在调用链上展示漏斗。** 前端调用链中用数字展示"召回 117 → 重排 102 → 入选 7 → 引用 1"，并允许管理员展开查看被淘汰的候选。追踪数据由第 4 节第 1 条提供。普通用户只看到汇总数字。
- **防止延迟恶化。** 重排容量调到 100 以后需要监控首字时间（TTFT）。如果 P95 恶化，优先启用 3.2 的级联方案，而不是降低质量。

## 6. 权限与安全评估

这次提交没有破坏权限链路，已核实的点如下：

- 重排前会执行 `authorizeModelEvidence`（`chat.service.ts:618,629`）。
- 小节救援只拉取已发布文档，结果在重排前经过同一次授权过滤。
- 最终引用还有一次 ACL 剔除（`citation-assembly.ts:1092`）。
- 重排缓存键包含 `userId` 和 `authorization.revision`。

需要关注的点：

- `retrieval-arms.ts:2107` 把完整 `metadata` 透传到候选上。目前对外发送的 `timeline_entry` 是逐个字段挑选的，所以没有泄露。但是 `processingTrace`、语义缓存中的 `citations` 和日志里可能带上这些字段，后续开发者也可能直接序列化整个候选对象，导致过度暴露。建议只透传重排需要的 3 个字段，或者在序列化边界做白名单。
- 地板放宽后，进入模型上下文的跨文档片段更多。权限本身不受影响，但上下文更容易混入不同密级或不同部门的内容（用户有权访问，但与问题无关）。如果存在按密级做提示词隔离的需求，应该把密级标签纳入选择逻辑。
- 保底组和 `floorExempt` 叠加以后，"必定进入上下文"的候选来源增加了。建议在追踪中标出每个入选候选的入选原因（`floor / guaranteed / exempt / summary / subquery / hop`），便于审计。
